# 当前开发与维护计划

## 1. 文档用途

本文件只记录当前系统的维护顺序、质量门槛和未完成工作。已经完成的阶段记录保存在
[`archive/development-history.md`](archive/development-history.md)，代码审查整改背景保存在
[`code-review-remediation-plan.md`](code-review-remediation-plan.md)。历史文档不是当前业务规范。

当前业务规则以以下文档为准：

- [`product-requirements.md`](product-requirements.md)；
- [`scoring-rules.md`](scoring-rules.md)；
- [`conversation-policy.md`](conversation-policy.md)；
- [`scheduling-policy.md`](scheduling-policy.md)。

## 2. 当前基线

系统当前是面向 BOSS、脉脉和猎聘的无人值守求职 Agent；脉脉 Run 仅处理系统推荐，
不发现、导入或回复普通私信。猎聘已完成 L4 写动作实现，但在 L5
真实页面验收和用户明确授权前，发布开关默认关闭：

- 硬性排除在 LLM 前执行，符合条件的职位再由受控 LLM 评分；
- 主动招呼需要总分不少于 80、模型建议沟通且确定性策略授权；
- 招聘方入站消息优先处理，明确索要简历可按资格规则发送默认附件；
- Rule Reply 和 Knowledge Reply 不依赖 LLM，开放式回复才调用模型；
- 电话和面试的具体时间始终需要用户确认；
- 浏览器写操作统一经过策略、幂等、目标复核、动作状态机和审计链；
- Worker、Run、平台会话和能力状态分别管理，不互相冒充。

## 3. 后续变更顺序

每项新需求或缺陷按以下顺序实施：

1. 复现或建立静态证据，明确外部行为和安全边界；
2. 先增加失败测试或验收夹具；
3. 修改最少的领域或适配器代码，不绕过策略引擎；
4. 数据模型变化创建独立 Alembic 迁移，并从空库验证完整迁移链；
5. 运行相关单元测试、PostgreSQL 集成测试、浏览器夹具测试和前端检查；
6. 同步专项文档和 README；
7. 真实平台验证必须单独获得用户授权，测试失败不得自动扩大写入范围。

## 4. 必须保持的回归范围

- 硬性排除、七个评分维度、80 分主动沟通边界；
- Rule、Knowledge、LLM、Human Reply Router 优先级和模型降级；
- 入站简历、联系方式和地点卡片资格判断；
- 电话/面试识别、人工确认和日历冲突；
- 消息、职位、草稿和动作幂等；
- `EXECUTING`、`OUTCOME_UNKNOWN`、对账和最终失败状态；
- BOSS、脉脉和猎聘的脱敏页面夹具；
- SQL 稳定分页、总数、数据库约束及迁移独立性；
- API 本机访问边界、前端中文状态和生产构建。

## 5. 当前待办与已知风险

1. 前端 Ant Design 公共依赖块约 507 KB（gzip 约 166 KB）。业务页面已经路由级拆分；
   后续只在无循环依赖且有构建收益证据时继续拆分。
2. 真实招聘平台 DOM 可能变化。选择器失效必须暂停对应平台并记录脱敏证据，不能猜测点击。
3. 正式数据库升级必须先备份并显式执行 `alembic upgrade head`；代码任务不得自行迁移正式库。
4. 历史 `LOW_SCORE_DECLINE` 动作类型只为旧审计记录保留，不允许创建新动作。
5. 确定性评分引擎仍由硬过滤状态计算和 Fake LLM 测试适配器读取，未满足安全删除条件。

## 6. 猎聘平台接入

### 6.1 L0 只读勘察结论（已完成）

2026-08-01 已在用户手动登录的专用 Chrome 会话中完成只读勘察。勘察期间没有投递、
发送消息、上传文件或修改简历；临时打开的职位、搜索和简历页面均已关闭，消息抽屉已收起。

已确认的页面契约：

- 允许域名至少包含 `c.liepin.com` 和 `www.liepin.com`；候选人首页是本项目唯一常驻的
  猎聘职位列表页，不自动打开或轮询独立的 `/zhaopin/` 搜索页；
- 首页推荐列表一次可见多条职位。职位链接
  存在 `/job/{id}.shtml` 和 `/a/{id}.shtml` 两种路径，并在查询参数中携带 `job_id`；
  规范化时以 `job_id` 为首选稳定身份，路径 ID 为回退证据，去除会话型跟踪参数；
- 首页职位卡可以读取标题、地点、薪资、经验、学历、公司、行业、招聘人及招聘人身份；
  “猎头顾问”和企业 HR 在卡片及详情中可区分，现有“猎头不主动招呼”规则可使用该证据；
- 职位详情页可稳定读取标题、薪资、地点、经验、学历、招聘人数、更新时间、福利、招聘人、
  招聘人身份、公司、职位介绍和公司简介。首页卡片只用于预筛；需要完整 JD 时允许创建一个
  临时详情页，完成硬过滤、评分及获授权的“聊一聊”或“投简历”动作后关闭。这里的
  “不打开职位页面”是指不再打开独立职位列表页，不代表用首页摘要代替完整 JD；
- 职位详情同时存在“投简历”和“聊一聊”。“聊一聊”用于主动招呼；招聘方明确索要简历且
  现有入站简历规则允许时，Agent 可以在身份一致的关联职位上自动点击“投简历”；
- “我的沟通”是嵌入页面的消息抽屉，不是独立消息 URL。会话项包含稳定 IM 对端标识、
  未读状态、招聘人、公司、时间和最后消息；消息详情通过 `receive/send` 语义类区分方向，
  输入区包含文本框、发送按钮和通用上传控件；
- 会话列表当前只展示 180 天内会话，因此本地消息历史和出站消息防重证据必须继续保留，
  不能把平台列表缺失视为未沟通过；
- `/resume/edit` 同时包含在线简历和“附件简历”区块，用户已手动维护在线简历和附件简历。
  猎聘 Agent 不新增、编辑、刷新、上传或删除简历；发送时只使用平台已有简历。“投简历”
  如果出现简历选择或确认步骤，只能选择已登记的现有默认简历，不得进入简历维护流程或
  使用聊天中的通用文件上传控件；

L0 结论：猎聘可以复用现有职位、评分、Reply Router、策略、动作队列、对账和审计领域
流程，但需要独立的平台页面适配器。不得把 BOSS 的刷新、虚拟列表、默认招呼或简历动作
直接套用到猎聘；猎聘当前范围包含首页职位发现、临时详情读取、“聊一聊”、普通沟通和
基于明确简历请求的“投简历”。

### 6.2 L1：平台模型与脱敏夹具（已完成）

完成记录：已增加 `LIEPIN` 平台模型及只读适配入口；选择器已按平台拆分并独立版本化，
旧统一配置已删除；已建立职位、消息、确认流程和异常状态脱敏夹具，并覆盖猎聘两类职位
链接、编码 IM 标识、登录/验证/结构变化、目标不一致、重复首页和共享首页交互冲突。
本阶段没有把猎聘加入 Worker Run，也没有启用猎聘真实发现或写动作。

1. 增加 `LIEPIN` 平台枚举和允许域名；
2. 将统一的 `config/browser-selectors.json` 拆分为独立平台文件：
   `config/browser-selectors/boss.json`、`maimai.json` 和 `liepin.json`。每个平台独立维护
   `platform`、`version`、允许域名及本平台实际使用的选择器；
3. 配置加载器在启动时读取全部平台文件并组装为统一的 `BrowserSelectorsConfig`，保持
   现有适配器调用方式不变。平台文件缺失、重复、文件内平台名不匹配或结构校验失败时，
   必须启动失败，不能回退到猜测选择器；
4. 将选择器结构按 `session/job_list/job_detail/conversation/resume_action` 能力分块；公共
   会话字段保持必需，其他能力块按平台声明。平台校验器必须保证 BOSS、脉脉和猎聘各自
   运行所需的能力完整，不得用空字符串或伪造选择器填充不存在的页面能力；
5. 先原样迁移 BOSS 和脉脉当前生效配置并删除旧统一文件，不保留两套并行配置来源；增加
   配置加载、独立版本、缺失平台、重复平台和非法文件测试，确认拆分前后页面行为一致；
6. 猎聘首页是职位列表和消息抽屉共享的唯一用户标签页。页面登记必须明确共享 target，
   不能创建两个猎聘首页；同一 Worker 内消息发现、消息动作、职位发现和职位动作必须串行，
   每次切换前验证当前页面状态，完成后恢复首页且收起 Agent 打开的消息抽屉；
7. 如果检测到用户正在输入未发送文本、页面存在确认弹窗或页面状态无法安全恢复，必须暂停
   当前猎聘循环，不覆盖用户输入、不强行关闭弹窗，也不继续职位扫描；
8. 建立首页职位列表、职位详情、消息列表、会话详情、“聊一聊”和“投简历”确认流程的
   脱敏 HTML 夹具；
9. 为 `/job/`、`/a/` 两类职位链接实现统一 ID 规范化；
10. 增加登录失效、验证码、页面结构变化、同角色多页面、共享首页状态冲突和目标身份不一致
    的失败夹具；
11. 选择器优先使用稳定语义类、URL 和数据属性，带构建哈希的类名只能作为辅助证据。

验收标准：配置只存在一个权威来源，三个平台可以独立修改选择器版本；所有猎聘页面只读
解析测试通过；异常页面返回明确状态码并禁止写动作；BOSS 和脉脉既有夹具无回归。

### 6.3 L2：职位发现、硬过滤与评分（已完成）

完成记录：猎聘 Run 已接入 Worker，但严格限定为只读职位发现和评分。Worker 只读取唯一
`c.liepin.com/` 首页，按当前顺序分批处理卡片并滚动加载，不刷新首页、不创建独立搜索页；
明显无关标题不打开详情，相关或不确定标题每次只打开一个临时详情，读取后立即关闭。
规范化职位 ID、跨 Run 发现记录、职位内容哈希和观察快照共同防止重复打开和评分；详情
失败的单个职位仍按既有队首重试规则恢复。结构化招聘人身份会进入解析和评分，明确猎头
不会成为主动沟通候选。满足条件的企业职位只记录 `PROACTIVE_CONTACT_CANDIDATE`，不会
创建草稿、动作或浏览器写入；猎聘只读执行器对任何误入的写命令均返回
`PLATFORM_WRITES_NOT_ENABLED`。职位中心、总览和 Run 状态沿用现有跨平台接口展示猎聘。

本阶段新增 `jobs.recruiter_role` 迁移，用于保存 `HEADHUNTER / DIRECT_EMPLOYER / UNKNOWN`
结构化证据；旧数据保留并默认为 `UNKNOWN`。消息发现、主动招呼、回复和投递仍属于 L3/L4。

1. 新增猎聘首页职位发现适配器，把唯一猎聘首页登记为常驻 `JOB_LIST` 页面，不创建
   `/zhaopin/` 搜索页；
2. 按首页当前推荐顺序增量读取职位卡，通过页面滚动获取后续推荐，不主动刷新首页；
3. 先执行标题三态预筛，再为相关或不确定职位临时打开一次详情读取完整 JD；硬性排除先于 LLM；
4. 已处理职位使用规范化 `job_id`、正文哈希和观察记录去重；临时详情完成处理后关闭，
   已确认无关或正文未变化的职位不得重复打开；
5. 招聘人明确为猎头时仍可保存和评分，但禁止创建主动沟通或主动投递动作；
6. 职位中心和总览使用现有跨平台查询展示 `LIEPIN` 数据。

验收标准：明显无关职位不调用 LLM；硬过滤职位不评分；相同正文不重复打开和评分；满足
条件的非猎头职位生成受策略约束的候选动作，但本阶段不启用真实写执行。

### 6.4 L3：消息发现、关联职位与 Reply Router

1. 新增猎聘消息抽屉适配器，不主动刷新页面；按会话稳定 IM 标识、最后消息和本地游标增量扫描；
2. 同时导入 `INBOUND/OUTBOUND`，保留 180 天平台可见范围之外的本地历史；
3. 读取关联职位、招聘人身份和完整消息历史，接入现有资格成熟度与 Reply Router；
4. 到岗、薪资、地点、工作模式和学历性质继续优先 Rule/Knowledge，不调用 LLM；
5. 已存在后续出站消息、双方已明确不合适或动作结果未知的会话不得重复发送；
6. 消息处理优先于职位发现；完成一批消息及其动作后收起 Agent 打开的抽屉，再允许首页职位
   扫描。页面状态恢复失败时暂停猎聘 Run，不能让两个流程争用同一首页；
7. 消息中心展示猎聘会话、关联职位、资格、草稿来源和动作状态。

验收标准：规则回复不调用 LLM；历史出站消息阻止旧草稿补发；新入站消息仍可处理；电话
和面试具体时间继续进入人工确认。

完成记录：猎聘 Worker 已按“消息优先、职位随后”串行运行。消息适配器在唯一猎聘首页中
打开消息抽屉，增量导入入站、出站、关联职位、招聘人身份和对话历史；只关闭 Agent 本轮
打开的抽屉，用户交互、身份异常或首页恢复失败时暂停本轮，不继续职位扫描。新入站消息已
接入通用资格判断、Reply Router 和排期确认，可生成带来源的规则、知识库或 LLM 草稿；L3
不创建或执行猎聘外部动作。所有 L3 猎聘草稿持久化为不可派发，未来进入 L4 后也不会补发
本阶段生成的历史草稿。消息中心沿用跨平台接口展示猎聘会话、关联职位、资格和草稿来源。

### 6.5 L4：猎聘动作执行、回读与审计（已完成）

完成记录：猎聘“聊一聊”、普通回复和基于明确入站请求的“投简历”已接入通用
`ActionQueue`、动作尝试、回读、对账和审计链。消息动作保留当前抽屉到本轮执行完成，职位
动作每次只保留一个 Worker 创建的临时详情页，动作后按页面所有权关闭。执行前重新核对
平台、职位、公司、招聘人和会话；写入前失败可按既有状态机处理，写入后无法回读进入
`OUTCOME_UNKNOWN` 且不直接重发。投简历只允许选择系统已登记、平台页面中名称完全一致的
现有默认简历，不上传或维护简历。L3 历史草稿继续保持 `dispatch_enabled=false`，不能补发。

代码能力由 `LIEPIN_WRITES_ENABLED` 控制，默认 `false`。这是 L4 到 L5 的一次性发布安全边界，
不是灰度等级、配额或长期业务开关；L5 真实单次验收和用户明确授权前不得改为 `true`。
L4 没有新增数据字段；继续使用 L3 已迁移的 `generated_drafts.dispatch_enabled`，因此本阶段
不创建新的 Alembic 迁移。

1. 猎聘实现“聊一聊”“普通回复”和“投简历”三类写动作；
2. 每个动作执行前重新核对平台、职位 ID、公司、招聘人、会话及当前策略；
3. 三类动作分别建立唯一定位、成功回读、已执行回读和失败回读夹具，使用相互独立的
   动作类型、幂等键和发送指纹；
4. 招聘方明确索要简历、关联职位身份可靠、没有已证实硬阻断且尚未发送时，可以自动创建
   “投简历”动作；仅有职位浏览或普通招呼不能自动授权投简历；
5. 执行器不得新增、编辑、刷新、上传或删除简历，也不得使用聊天通用上传控件；如“投简历”
   流程要求选择简历，只能选择系统中登记的猎聘平台已有默认简历（在线简历或附件简历），
   并在提交前再次核对类型和名称；
6. 写入前创建 Action Queue 和审计记录，结果不可确认进入 `OUTCOME_UNKNOWN`，只读对账，
   不直接重试；同一入站简历请求完成“投简历”后，不得再创建聊天文件上传或第二次投递动作。
7. L3 产生的不可派发历史草稿不得直接启用；必须基于仍然有效的新入站消息重新生成并再次
   经过策略、身份和页面复核。

验收标准：同一职位主动招呼、同一消息回复和同一明确简历请求最多产生一个可执行动作；模拟
页面能够覆盖成功、写入前失败、写入后结果未知、目标变化和重复执行。

### 6.6 L5：完整回归与正式启用

## 7. 完成标准

一次变更只有同时满足以下条件才算完成：

- 需求对应测试通过，既有回归没有新增失败；
- 数据库迁移能在全新 PostgreSQL 数据库从首版升级到最新版本；
- API、策略、数据库和前端展示使用相同术语；
- README 的安装、启动和恢复步骤与代码一致；
- 没有新增未使用配置、重复动作路径或无法解释的状态字符串；
- 未验证内容和真实平台风险在交付报告中明确列出。
