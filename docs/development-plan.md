# 分阶段开发计划

## 1. 文档用途

本文是当前版本的实施依据，描述从现有可运行代码迁移到“LLM 评分 + 自动沟通闭环”的开发顺序。产品规则以以下文档为准：

- `product-requirements.md`
- `scoring-rules.md`
- `conversation-policy.md`
- `scheduling-policy.md`
- `architecture.md`
- `data-model.md`
- `api-design.md`

每个阶段必须完成对应迁移、测试和文档同步后才能进入下一阶段。不得因为后续代码已经存在，就跳过前置的数据兼容和安全校验。

## 2. 现有代码基线

### 2.1 已具备能力

后端已具备：

- Python 3.13、FastAPI、Pydantic v2、SQLAlchemy 2、Alembic 和 PostgreSQL 工程基础。
- 候选人资料、技能、行业经历和求职策略管理。
- 模拟 JD 导入、规则解析、职位生命周期和内容去重。
- 七维确定性评分、硬性排除、等级和风险理由。
- 知识项、附件简历元数据、模拟对话、消息和草稿。
- BOSS/脉脉只读页面适配，以及 BOSS 当前职位的受控真实联调。
- 人工确认、动作队列、执行尝试、审计和发送幂等。
- 自动化配置、限速判断和自动动作创建。
- 电话/面试邀请解析、本地假日历冲突检查和时间确认。

前端已具备：

- 候选人资料、策略、职位、对话、浏览器、动作、自动化和排期页面。
- Vite、React、TypeScript 和 Ant Design 基础。

当前验证基线：

- `pytest tests/unit -q`：81 项通过。
- `ruff check apps packages adapters tests`：通过。
- `mypy apps packages adapters`：通过。
- `npm run test -- --run`：1 项通过。
- `npm run build`：通过，但主包约 1 MB，存在分包警告。
- `pytest tests/integration -q`：因未配置 `TEST_DATABASE_URL`，2 项跳过；PostgreSQL集成行为尚未验证。
- 本轮未运行 Alembic 升降级验证。

### 2.2 与目标设计的主要差距

| 领域 | 现有实现 | 目标实现 |
|---|---|---|
| LLM | 只有 `FakeLlmJobParser` | 统一 `LLMProvider`，开发阶段接入千问 |
| 评分 | 程序按七个固定公式计分 | LLM 生成七维分和建议，程序校验并执行硬性排除 |
| 主动沟通 | 默认70分，可配置到60分 | 固定最低80分且模型必须建议主动沟通 |
| 入站回复 | 关键词意图 + 模板；多种情况确认 | LLM识别意图并生成事实受限回复，仅时间类确认 |
| 低分岗位 | C级拒绝自动处理 | 低于60分自动礼貌婉拒一次 |
| 简历发送 | 明确索要且通常需要确认 | 60分以上，明确索要或积极反馈时自动发送 |
| 策略绑定 | 对话只绑定职位 | 对话绑定选定策略和最新有效评分 |
| LLM审计 | 无调用记录 | 保存供应商、模型、提示词版本、耗时、Token和失败码 |
| Agent运行 | 只有单次读取/单次dispatch | 运行、暂停、心跳、轮询、熔断和恢复 |
| 浏览器覆盖 | 真实职位详情只读初步可用 | 职位列表、聊天、招呼和附件简历的稳定适配 |
| 前端 | 展示旧规则和手动流程 | 展示模型状态、Agent运行状态和80/60决策 |

### 2.3 必须保留的现有能力

- 硬性排除、职位生命周期、导入幂等和动作阻断保持独立。
- 评分历史和动作历史追加保存，不覆盖旧记录。
- 浏览器适配器不直接决定评分、回复或发送。
- 动作原子占用、发送指纹、尝试记录和 `OUTCOME_UNKNOWN` 对账继续复用。
- 验证码、登录异常、页面变化和目标身份不一致时停止写操作。
- 时间空闲不能绕过电话或面试具体时间确认。

## 3. 总体实施顺序

```text
阶段一：数据兼容与配置基础
→ 阶段二：统一 LLM 端口与千问适配
→ 阶段三：LLM 职位解析和评分
→ 阶段四：LLM 对话、低分婉拒和简历决策
→ 阶段五：Agent 调度与自动动作闭环
→ 阶段六：招聘平台适配和模拟端到端验证
→ 阶段七：前端控制台和受控真实联调
→ 阶段八至十三：按第 12 节完成 BOSS 无人值守闭环与灰度验收
```

阶段一至四不执行真实招聘网站写操作。阶段五先使用假动作执行器。只有阶段六的模拟页面验收通过后，阶段七才允许在用户专用登录窗口进行限量真实联调。
阶段七完成后仍只代表具备受控真实联调能力；是否达到无人值守必须以第 12 节阶段八
至十三的验收结果为准。

## 4. 阶段一：数据兼容与配置基础

实施状态：已完成（2026-07-23）。已新增0007迁移、LLM环境配置、策略优先级、对话评分绑定字段、LLM调用审计表、评分模型元数据和80/60阈值保护。历史评分保留展示但 `automation_eligible=false`。空库升级暴露的0005重复字段问题已做兼容修复。

### 4.1 目标

先让数据库和配置能够表达新规则，同时保证现有数据可读取、迁移可回滚。

### 4.2 实施范围

1. 为求职策略增加 `priority`，正整数且数值越小优先级越高。
2. 为对话增加 `strategy_id` 和 `latest_job_score_id`。
3. 新增 `llm_invocations`，记录调用用途、供应商、模型、提示词版本、输入哈希、状态、响应 ID、耗时、Token、失败码和尝试序号。
4. 扩展评分记录：
   - `prompt_version`
   - `llm_invocation_id`
   - `llm_recommends_proactive_contact`
   - `llm_contact_reason`
   - `automation_eligible`
5. 评分明细增加 `evidence_refs`。
6. 为低分婉拒增加动作类型和消息状态。
7. 将自动招呼最低分迁移为80，将自动简历最低分迁移为60；服务端禁止配置到更低。
8. 增加 LLM 环境配置：
   - `LLM_PROVIDER`
   - `LLM_API_KEY`
   - `LLM_BASE_URL`
   - `LLM_MODEL`
   - `LLM_TIMEOUT_SECONDS`
   - `LLM_MAX_RETRIES`
9. API Key 只从环境变量读取，不进入数据库、响应或日志。

### 4.3 数据迁移要求

- 新增一条 Alembic 迁移，不修改已有迁移文件。
- 现有策略按创建时间生成稳定优先级。
- 现有对话暂不自动绑定策略；第一次处理入站消息时执行策略选择。
- 现有评分标记为旧评分版本，可展示但不可授权新自动动作。
- 现有70分配置迁移到80；现有大于80的配置保持不变。
- 现有简历阈值小于60时迁移到60，大于60时保持不变。

### 4.4 测试

- Alembic 从空库升级到最新版本。
- 从当前 `20260721_0006` 升级并验证数据回填。
- 最新迁移单步降级后再升级。
- 数据库默认值、外键、检查约束和唯一约束。
- 配置缺少 API Key 时返回明确的“模型未配置”，不得输出密钥。

### 4.5 验收标准

- 新旧职位、评分、对话和动作记录均可读取。
- 旧评分不能误触发80分主动沟通。
- 数据迁移不删除现有候选人资料、策略、职位或审计记录。

## 5. 阶段二：统一 LLM 端口与千问适配

实施状态：已完成（2026-07-23）。已新增供应商无关的六类 LLM 端口与 Pydantic
契约、千问 OpenAI 兼容非流式 JSON 适配器、明确错误分类、仅网络连接失败的一次重试、
离线 Fake Provider、调用元数据写入服务和显式手动冒烟脚本。评分与对话业务链路仍保持
原实现，按阶段三、四分别切换。

### 5.1 目标

建立供应商无关的 LLM 领域端口，并完成千问开发适配；后续切换智谱只新增适配器。

### 5.2 领域接口

统一接口至少支持：

- `parse_job`
- `score_job`
- `classify_message`
- `generate_greeting`
- `generate_reply`
- `evaluate_conversation`

每个方法使用独立 Pydantic 输入输出模型，不传递供应商原始对象。

### 5.3 千问适配器

- 使用 OpenAI 兼容 Chat Completions 接口。
- 使用 JSON 结构化输出。
- 固定系统提示词，JD 和招聘消息作为不可信结构化数据传入。
- 默认非流式调用。
- 明确区分超时、限流、认证失败、服务端错误、空响应和非法 JSON。
- 仅对明确未产生业务结果的网络失败重试一次。
- 保存 `llm_invocations` 元数据，不保存完整密钥和无必要的完整提示词。

### 5.4 测试替身

- `FakeLlmProvider` 返回固定合法结果，用于领域和集成测试。
- HTTP 适配器测试使用模拟响应，不调用真实千问、不产生费用。
- 提供手动冒烟命令；只有本机配置 API Key 时才执行，并标记为非默认测试。

### 5.5 测试

- 合法 JSON 响应。
- Markdown 代码块包裹、空内容、非 JSON、字段缺失和枚举错误。
- 401、429、5xx、连接失败和超时。
- 提示注入文本不能改变系统评分契约或请求工具调用。
- 日志、异常和响应中不包含 API Key。

### 5.6 验收标准

- 领域包不导入千问 SDK或供应商专用类型。
- 切换 `FAKE/QWEN` 只需要配置和依赖注入。
- 默认测试完全离线。

## 6. 阶段三：LLM 职位解析和评分

实施状态：已完成（2026-07-23）。新评分链路已切换为 LLM 七维输出，程序负责维度、
上限、精度、求和和证据校验，并独立执行硬性排除、等级、职位状态和 80 分主动沟通
授权。评分保存模型调用、提示词版本、证据和输入快照；普通请求保持幂等，重新评估
接口通过 `Idempotency-Key` 幂等追加评分。多策略选择规则已实现为独立领域能力，
留待第四阶段入站对话绑定时编排。

### 6.1 目标

将新评分链路切换为“程序硬性排除 + LLM 七维评分 + 程序校验和授权”，旧规则评分只保留历史展示和测试迁移用途。

### 6.2 实施顺序

1. 保留现有 JD 规范化和薪资解析，作为模型输入和硬性排除依据。
2. 调用 LLM 提取职责、必须技能、优先技能、年限、级别和风险。
3. 程序执行全部硬性排除规则。
4. 将策略、JD、候选人可信资料、七维量表和硬性排除结果提交给评分模型。
5. 校验：
   - 七个维度完整且不重复；
   - 每个分数未超过维度上限；
   - 证据引用来自输入；
   - 模型总分与维度和一致；
   - 理由和风险长度受限；
   - 模型不能解除硬性排除。
6. 程序根据七维和计算最终整数总分和 A/B/C 等级。
7. 程序计算 `automation_eligible`：
   - 未硬性排除；
   - 职位开放且未过期；
   - 总分至少80；
   - 模型建议主动沟通。
8. 保存评分、明细、证据、模型调用和输入版本。
9. 支持显式重新评估 API，普通重复请求继续幂等。

### 6.3 多策略

- Agent主动发现任务只使用运行绑定的策略。
- 未绑定策略的入站对话对所有启用策略评分。
- 选择未硬性排除且分数最高的结果；同分时选择优先级最高的策略。
- 全部硬性排除时选择最高优先级策略的公开原因生成婉拒。

### 6.4 失败策略

- 模型不可用或输出非法时不产生新的有效评分。
- 不回退到旧确定性公式冒充新评分。
- 不主动沟通、不发送简历。
- 输入版本未变化的既有新评分可继续用于低风险模板回复；旧规则评分不可复用。

### 6.5 测试

- 每个维度的0分、满分、越界、缺失和非法证据。
- 维度求和不一致、未知维度、重复维度和非数字。
- 每条硬性排除的命中与反例。
- `59/60/69/70/79/80/100` 边界。
- 79分且模型建议主动沟通仍不允许；80分但模型不建议也不允许。
- 多策略选择、同分优先级、全部排除和策略停用。
- 评分指纹、重新评估和并发重复请求。
- PostgreSQL持久化及API集成测试。

### 6.6 验收标准

- 新评分全部来自 LLM 合法输出。
- 最终动作不能绕过硬性排除和80分门槛。
- 评分详情能展示模型、提示词版本、证据、理由和风险。

## 7. 阶段四：LLM 对话、低分婉拒和简历决策

实施状态：已完成（2026-07-23）。入站对话会绑定或刷新启用策略下的最新 LLM 评分；
低分、硬排除或非开放职位优先生成一次性脱敏婉拒。60 分以上使用 LLM 多意图识别和
事实 UUID 受限生成，缺少事实、低置信度和敏感请求使用安全自动口径，只有具体时间
创建确认任务。简历决策校验当前对话消息 UUID、60 分门槛、硬排除、附件唯一匹配和
重复发送。新增 0008 迁移保存独立低分婉拒开关；本阶段仍不执行真实平台写操作。

### 7.1 目标

实现招聘方消息到安全回复或简历动作的自动决策，仅电话和面试具体时间进入人工确认。

### 7.2 消息处理顺序

```text
幂等导入消息
→ 校验或刷新对话绑定评分
→ 低于60分：LOW_SCORE_DECLINE
→ 60分及以上：LLM多意图识别
→ 检索候选人可信事实和最近对话
→ 生成事实受限回复
→ 识别明确简历请求或积极反馈
→ 程序执行内容、时间、简历和重复检查
→ ALLOW_AUTO / REQUIRE_CONFIRMATION / DENY
```

### 7.3 低分婉拒

- 低于60分优先于普通回复和排期。
- 只使用地点、工作模式、薪资或岗位方向等可公开原因。
- 不透露具体分数、公司黑名单和内部风险标签。
- 相同对话只发送一次；后续消息默认不再自动回复。

### 7.4 普通回复

- 60分及以上默认自动回复。
- LLM只能引用知识库事实 ID。
- 缺少事实时使用保守口径或澄清问题，不创建普通人工确认。
- 身份证、银行卡、验证码、家庭隐私和公司机密自动拒绝披露。
- 薪资、到岗和离职原因只使用用户配置的公开口径。
- 电话和面试具体时间交给现有排期模块，必须确认。

### 7.5 简历发送

- 明确索要简历，或模型识别到有消息证据的积极反馈。
- 当前分数至少60且未硬性排除。
- 模型必须返回引用的招聘方消息 ID、反馈类型和置信度。
- 程序校验消息属于当前对话。
- 附件必须已登记、平台内唯一匹配且方向相符。
- 相同对话和简历只发送一次。
- 反馈不明确时不发送，也不创建人工确认。

### 7.6 测试

- 59分婉拒、60分普通回复、80分对话回复。
- 婉拒原因脱敏和只发送一次。
- 有事实、无事实、过期事实和禁止事实。
- 多意图消息和时间意图优先级。
- 明确索要、积极反馈、模糊反馈和伪造消息 ID。
- 重复简历、附件缺失和方向不匹配。
- LLM故障时不发送未经校验的自由文本。

### 7.7 验收标准

- 非时间类消息不产生普通确认任务。
- 不存在事实幻觉或敏感信息泄露。
- 低分、普通回复、时间确认和简历发送四条路径可审计且互不冲突。

## 8. 阶段五：Agent 调度与自动动作闭环

实施状态：已完成（2026-07-23）。已新增 `agent_runs`、`agent_run_events`、动作运行
追溯字段和 0009 迁移；实现启动、暂停、恢复、状态查询和单次 tick。轮询使用数据库
短租约，租约过期可由新工作进程恢复；消息、草稿和动作继续使用既有唯一指纹避免重复。
连续模型失败达到配置阈值、平台会话异常、执行失败或 `OUTCOME_UNKNOWN` 会在当前循环
暂停运行。阶段五自动循环只使用离线 Fake 执行器，不连接真实招聘网站。

### 8.1 目标

从单次 API 调用升级为可启动、暂停、恢复和监控的 Agent 运行。

### 8.2 数据与服务

- 新增 `agent_runs`：平台、策略、状态、心跳、游标、计数、暂停原因和版本。
- 新增 `agent_run_events`：追加记录发现、评分、消息和动作事件。
- 单实例先使用数据库租约和短周期轮询，不提前引入 Redis、Celery 或消息队列。
- 同一用户和平台最多一个活动运行。

### 8.3 循环职责

1. 检查全局、平台和策略开关。
2. 检查登录、验证和平台暂停状态。
3. 读取职位或新消息。
4. 幂等导入。
5. 解析和评分。
6. 生成候选动作并通过策略引擎授权。
7. 创建唯一动作。
8. 调用执行器并回读结果。
9. 更新游标、心跳和限速计数。

### 8.4 熔断与恢复

- 验证码、登录失效、页面结构变化、身份不匹配和连续模型失败时暂停运行。
- `OUTCOME_UNKNOWN` 阻断同一目标后续写操作，先对账。
- 进程重启后从数据库租约和游标恢复，不重复发送。
- 用户暂停立即阻止新动作，已经进入 `EXECUTING` 的动作只完成当前原子步骤并回读。

### 8.5 测试

- 单运行约束、租约超时和进程恢复。
- 小时/每日限速。
- 同一职位、消息和动作重复轮询。
- 模型故障、浏览器故障和连续失败熔断。
- 暂停时无新动作。
- `OUTCOME_UNKNOWN` 对账阻断。

### 8.6 验收标准

- 使用假浏览器和假 LLM 连续运行时不重复招呼、回复或发送简历。
- 任一安全异常能在一次循环内暂停对应平台。
- 所有自动动作能追溯到运行、评分、模型调用和策略决策。

## 11. 无人值守目标的当前审查结论

审查日期：2026-07-23。

前述阶段一至七的“已完成”仅表示对应领域能力、模拟流程或受控真实联调入口已经
实现，不表示系统已经达到 BOSS 全站无人值守。当前真实能力边界是：

- 可以通过用户手动登录的本机浏览器读取当前打开的 BOSS 职位详情或具体对话；
- 可以导入 JD，使用千问解析和七维评分，并由程序执行硬性排除、80 分门槛和猎头
  分数封顶；
- 可以在唯一匹配的当前对话中使用原生 CDP 发送已授权文本并回读结果；
- Worker 可以轮询当前已经绑定职位和评分的打开会话；
- 电话和面试具体时间仍进入人工确认；
- 不保存 BOSS 账号密码，不绕过验证码、设备验证或平台风控。

当前尚不能宣称无人值守，原因如下：

| 领域 | 当前状态 | 无人值守缺口 |
|---|---|---|
| 职位发现 | 具备列表夹具读取和单详情真实读取 | 未在真实 BOSS 中实现列表分页、虚拟滚动、自动打开详情、返回列表和断点游标 |
| 消息发现 | 具备对话列表夹具和单会话真实读取 | 未自动遍历全部消息、未读和新招呼，不能自动切换并恢复列表位置 |
| 职位绑定 | 当前会话需先手动导入并绑定职位 | 新会话不能自动取得完整 JD、唯一职位 ID、策略和最新有效评分 |
| 回复生成 | 支持 LLM 意图和事实受限回复 | 回复请求尚未完整包含策略、JD、评分维度、风险和会话状态；真实测试出现无效保守回复 |
| 主动沟通 | 单职位真实招呼已联调 | 未接入职位发现循环，未完成跨职位去重、公司冷却、每日配额和列表恢复 |
| 简历发送 | 夹具和领域规则已实现 | 未完成真实消息证据识别、站内附件枚举、唯一选择、发送回读和跨会话去重联调 |
| 时间安排 | 本地假日历和确认流程已实现 | 未接入真实日历，未实现无人值守发现邀请后及时通知用户和确认过期恢复 |
| Worker | 数据库租约、心跳和当前会话同步已实现 | 服务层默认仍保留 Fake 执行器；缺少正式运行模式隔离、单实例进程锁和自动拉起 |
| 对账恢复 | 有 `OUTCOME_UNKNOWN` 状态和阻断 | 缺少通用平台回读对账任务、对账 API、可审计的安全重试和控制台操作 |
| 稳定性 | 有单元测试和脱敏页面夹具 | 尚未完成 PostgreSQL 全量集成、真实 DOM 回归、8 小时耐久和重启恢复测试 |
| 平台范围 | BOSS 单会话受控联调 | 脉脉写操作和无人值守均未实施 |

本次真实联调额外暴露了以下必须修复的问题：

1. 真实 BOSS 的会话、消息和职位字段与早期夹具属性不同，选择器必须继续按版本维护。
2. “代招公司”证据曾在规范化时丢失，导致猎头封顶未生效；后续所有安全信号必须
   保留原始证据并由程序确定性校验。
3. 普通回复只收到单条消息时，模型无法利用地点策略和评分风险，可能生成无业务价值
   的保守回复。
4. 旧版模拟 Worker 可以把动作记录为成功但不产生平台投递；正式模式必须禁止加载
   Fake 执行器，并在启动时拒绝多个 Worker。
5. 富文本编辑器填充和按钮可用状态存在异步延迟；执行器必须等待页面状态稳定，并在
   结果不明确时进入对账，不能盲目重试。

## 12. 达到 BOSS 无人值守的后续阶段

总体顺序：

```text
阶段八：单会话生产闭环加固
→ 阶段九：消息列表自动发现与职位绑定
→ 阶段十：职位列表自动发现、评分与主动沟通
→ 阶段十一：简历、电话、面试和真实日历协同
→ 阶段十二：对账、监控、进程治理和耐久验证
→ 阶段十三：小流量无人值守灰度与正式验收
```

必须按顺序推进。阶段八至十二未全部验收前，不得开启 BOSS 全列表无人值守写操作。

### 12.1 阶段八：单会话生产闭环加固

实施状态：部分完成。

目标：将当前“打开一个已绑定会话即可工作”的模式做成可靠的最小生产闭环，为跨
会话自动化提供稳定基础。

实施范围：

1. 回复生成请求增加当前求职策略、结构化 JD、最新有效评分、维度分、匹配理由、
   风险、工作模式和地点冲突。
2. 候选人资料与知识项统一生成可追溯事实引用；策略偏好使用独立受信上下文，不伪装
   成简历事实。
3. 针对普通招呼、工作模式未知、地点冲突、薪资询问、技术问题、到岗问题和敏感问题
   定义回复目标与安全降级。
4. 同一批连续入站消息按会话聚合处理，只回复最新有效语义，不连续回复旧招呼。
5. 原生 CDP 文本执行器完善富文本输入、按钮状态等待、出站消息精确回读和重复内容
   检查。
6. Worker 正式模式必须显式使用真实执行器；测试模式才能使用 Fake。启动时增加
   单实例进程保护并记录执行器类型。
7. 建立通用 `OUTCOME_UNKNOWN` 对账服务：回读确认已发送、确认未发送或继续未知；
   只有确认未发送且授权仍有效时才允许创建安全重试。
8. 清理“直接修改数据库完成动作”的临时联调方式，所有编辑、批准、重试和对账必须
   通过服务/API 并记录审计。

测试范围：

- 普通招呼结合远程/济南策略生成有效澄清回复。
- 策略、JD、评分或事实缺失时不虚构。
- 同一会话连续两条招呼只生成一个有效动作。
- 富文本输入延迟、按钮延迟、重复文本、发送后延迟回读。
- `OUTCOME_UNKNOWN` 三种对账结果及并发对账。
- 正式模式误配置 Fake 执行器时启动失败。
- 两个 Worker 同时启动时仅一个取得运行资格。

验收标准：

- 单个真实会话连续完成至少 20 次“读取—决策—发送/确认—回读”且无重复、串话和
  虚假成功。
- 每条回复均能追溯到消息、职位、评分、策略、模型调用、策略决策和平台证据。
- 电话或面试具体时间 100% 不自动发送。

### 12.2 阶段九：消息列表自动发现与职位绑定

实施状态：未开始。

目标：无人值守发现全部未处理入站消息，安全切换会话，并在回复前自动绑定职位和
最新评分。

实施范围：

1. 适配真实 BOSS 消息列表、未读、新招呼和虚拟滚动 DOM，提取稳定会话 ID、招聘人、
   公司、职位、未读数和最后消息标识。
2. 增加消息发现游标：列表分区、滚动位置、最后会话 ID、最后消息 ID和扫描时间。
3. 状态机覆盖：
   `LIST_READY → OPENING_CONVERSATION → VERIFYING_TARGET → READING_MESSAGES
   → BINDING_JOB → DECIDING → RETURNING_TO_LIST`。
4. 每次会话切换后重新核对会话 ID、招聘人、职位和所选列表项；任何不一致立即停止
   写操作。
5. 优先使用平台稳定职位标识绑定已有职位；没有完整 JD 时打开“查看职位”，读取后
   返回原会话。
6. 无法唯一绑定职位、职位详情不可用或招聘方更换岗位时暂停当前会话并记录原因，
   不得猜测。
7. 新消息导入以 `(conversation_id, external_message_id)` 幂等；同一会话使用短租约
   防止并发处理。
8. 已完成、已婉拒、已暂停和存在未知结果的会话不得重复进入普通自动回复。

测试范围：

- 真实结构脱敏夹具：全部、未读、新招呼、虚拟滚动、无更多数据。
- 列表重排、招聘人重名、相同职位名、职位切换和详情新标签页。
- 新消息到达时列表变化、切换中页面变化和返回列表失败。
- 重启后从游标恢复；同一消息扫描多次只处理一次。
- 会话无法绑定、评分过期和 LLM 不可用时安全暂停。

验收标准：

- 自动遍历至少 100 个模拟会话，无串会话、漏掉已加载未读或重复回复。
- 真实受控联调连续处理至少 20 个不同会话，目标身份核对全部通过。
- 未绑定最新有效评分的会话不产生任何平台写操作。

### 12.3 阶段十：职位列表自动发现、评分与主动沟通

实施状态：未开始。

目标：自动发现新职位，完成 JD 导入、解析、评分，并仅对满足全部条件的职位发起
沟通。

实施范围：

1. 适配真实 BOSS 搜索列表、分页/虚拟滚动、推荐职位和列表过滤条件。
2. 增加职位发现游标和扫描任务，保存搜索条件、列表位置、已见职位 ID、最后扫描时间
   和下一次允许扫描时间。
3. 状态机覆盖：
   `SEARCH_READY → READING_CARD → OPENING_DETAIL → VERIFYING_JOB
   → IMPORTING → PARSING → SCORING → AUTHORIZING → CONTACTING/RETURNING`。
4. 自动执行“导入 JD → 千问解析 → 程序硬性排除 → 千问七维评分 → 程序校验和猎头
   封顶 → 动作授权”。
5. 工作模式未知、公司匿名、薪资不明确和招聘渠道不明时保留风险；缺少安全所需字段
   时禁止主动沟通。
6. 主动沟通必须同时满足：总分至少 80、模型建议、未硬性排除、职位开放、非猎头封顶、
   自动招呼开关、限速和去重。
7. 跨职位去重至少覆盖外部职位 ID、同公司同标题、相似 JD 和已经建立的会话。
8. 增加公司/招聘人冷却、每小时和每日扫描/招呼上限、工作时段和全局紧急停止。
9. BOSS 平台默认招呼必须回读真实文本；结果未知时暂停该职位和平台写入。

测试范围：

- 分页、虚拟滚动、列表刷新、广告卡片、匿名公司和职位关闭。
- 79/80 分边界、猎头 79 封顶、硬性排除、模型不建议和评分过期。
- 相同职位重复出现、同公司相似职位和已沟通职位。
- 扫描/招呼限速、工作时段、暂停和紧急停止。
- 打开详情产生新标签、返回列表、标签丢失和页面结构变化。

验收标准：

- 自动遍历至少 500 个模拟职位，导入和动作严格幂等。
- 真实灰度扫描至少 100 个职位，评分证据完整，未发生未评分先沟通。
- 只有满足全部 80 分规则的职位产生主动招呼；猎头职位主动招呼为零。

### 12.4 阶段十一：简历、电话、面试和真实日历协同

实施状态：部分领域能力完成，真实闭环未开始。

目标：在消息无人值守基础上完成招聘沟通后半程，同时保留具体时间人工确认。

实施范围：

1. 自动识别明确索要简历和带消息 ID 证据的积极反馈。
2. 读取真实 BOSS 站内附件列表，按岗位方向唯一选择；不自动上传本地文件。
3. 简历发送前重新校验职位分数、硬性排除、地点/模式、附件、会话和发送记录。
4. 简历发送后回读附件名称或平台消息，建立 `(conversation_id, resume_id)` 唯一记录。
5. 电话、视频和现场面试邀请自动解析并创建确认任务，通过站内控制台或通知渠道提醒
   用户。
6. 接入一个真实日历供应商，首选由用户决定 Google Calendar 或 Outlook Calendar；
   只读查忙和写事件使用独立授权。
7. 确认任务保存日历快照版本和有效期；发送前重新查冲突。
8. 对方改期、取消或变更形式时，新任务替代旧任务，不静默覆盖。

测试范围：

- 明确索要、积极反馈、模糊反馈、伪造消息证据和低分职位。
- 附件重名、缺失、方向不匹配、已经发送和发送结果未知。
- 明确时间、模糊时间、相对日期、时区、冲突、日历不可用和快照过期。
- 用户确认、修改、拒绝、超时和对方改期。

验收标准：

- 简历发送无重复、无错误附件、无低分或硬性排除职位发送。
- 所有具体电话和面试时间均有用户确认记录。
- 日历空闲不会自动授权对外时间回复。

### 12.5 阶段十二：对账、监控、进程治理和耐久验证

实施状态：未开始。

目标：让无人值守运行可观察、可停止、可恢复，并避免历史模拟进程或多实例造成错误。

实施范围：

1. Worker 进程锁、PID/实例登记、心跳过期检测、单实例启动和优雅停止。
2. API、Worker 和浏览器会话启动自检：数据库迁移、LLM、选择器版本、CDP、登录状态、
   执行器类型和自动化开关。
3. 控制台展示职位扫描、消息扫描、当前状态、游标、速率、最近动作、未知结果、确认
   任务和熔断原因。
4. 增加平台级紧急停止；停止后不再创建新动作，当前原子动作只允许完成回读。
5. 通用对账队列自动处理待回读动作；对账超时升级为人工处理。
6. 浏览器关闭、服务重启、网络中断、模型限流和数据库暂时不可用时按安全级别恢复。
7. 审计检查任务识别“数据库成功但平台不存在”“平台已发送但数据库未知”等差异。
8. 日志脱敏、数据保留周期、备份和恢复演练。

测试范围：

- 多 Worker、进程崩溃、租约过期、服务重启和浏览器重启。
- 数据库提交前后故障、平台点击前后故障和回读超时。
- LLM 401/429/5xx、CDP 断开、登录失效、验证码和 DOM 变化。
- 紧急停止、恢复、对账和审计差异修复。
- 8 小时与 24 小时耐久测试，监控数据库增长和资源泄漏。

验收标准：

- 任何时刻同一用户和平台只有一个有效 Worker。
- 进程或服务重启后从持久化游标恢复，不重复发送。
- 验证码、登录失效、页面变化或目标不一致时一个循环内停止全部平台写操作。
- 不存在无法追溯来源的成功动作。

### 12.6 阶段十三：小流量无人值守灰度与正式验收

实施状态：未开始。

目标：逐步扩大真实范围，以可量化结果决定是否进入日常无人值守。

灰度顺序：

1. 只读遍历消息列表，不发送。
2. 只读遍历职位列表并评分，不招呼。
3. 单日最多 5 个普通回复，主动招呼和简历关闭。
4. 单日最多 3 个主动招呼，普通回复限量，简历关闭。
5. 开启明确索要简历后的自动发送。
6. 扩大到配置的正式限额；时间类确认规则始终不变。

每一级至少运行一个完整工作日，只有以下指标全部满足才能升级：

- 串会话次数为 0。
- 重复消息和重复简历次数为 0。
- 未评分先写操作次数为 0。
- 猎头主动招呼次数为 0。
- 电话或面试具体时间自动承诺次数为 0。
- 页面身份不一致时继续写操作次数为 0。
- 所有成功动作均有平台回读证据。
- 所有未知结果均进入对账且没有盲目重试。

正式无人值守验收：

- 连续 8 小时运行无安全错误，通过后再完成 24 小时耐久验证。
- 至少处理 100 个真实职位和 20 个真实会话。
- 服务、Worker 或浏览器重启后能够恢复且不重复处理。
- 用户可以随时暂停，暂停后不产生新写操作。
- 未达到任何一项安全指标时自动降级到上一灰度级别或完全暂停。

## 13. 明确延期或不属于 BOSS 无人值守首版的范围

- 智谱适配器：千问闭环和无人值守灰度稳定后实现，复用 `LLMProvider`。
- 多用户认证和生产级组织权限。
- 分布式任务队列和多实例部署。
- 自动上传本地简历。
- 地图路线和实时通勤服务。
- 脉脉写操作与无人值守：BOSS 正式验收后单独立项。
- 验证码破解、滑块绕过、浏览器指纹伪装、代理池和平台反检测永不进入范围。

```

```
