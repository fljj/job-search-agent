# 电话、面试与日历策略

## 1. 适用范围

本文是电话沟通、视频面试、技术面试、现场面试、具体时间建议和日历冲突判断的权威规则。

核心原则：系统可以识别、查询、分析和生成建议，但任何包含具体沟通或面试时间的对外回复都必须先取得用户确认。

资格优先级：

- 电话沟通至少要求对话达到 `ROUGH_MATCH`，即岗位方向大体相关且没有已知明确冲突；
- 视频、技术和现场面试必须达到 `FULL_MATCH`，即岗位关键信息已经充分了解并符合策略；
- `UNKNOWN` 不得推进电话或面试，应先澄清岗位信息；
- `MISMATCH` 执行礼貌婉拒，不进入排期确认；
- 正式职位分只作为参考，不再以 60 分作为入站电话或面试的直接门槛；
- 电话或面试任何具体时间仍必须由用户确认。黑名单、欺诈风险和明确策略冲突优先于
  排期流程。

`FULL_MATCH` 的完整字段以 `conversation-policy.md` 为准。任何必需字段未知时不得因
日历空闲、招聘方催促或模型乐观判断而推进面试。

## 2. 时间邀请识别

系统应识别：

- 对方提出明确日期和时间。
- 对方提出日期但未给具体时间。
- 对方询问用户可用时间。
- 电话、视频、技术或现场面试类型。
- 预计时长和地点。
- 相对日期，例如“明天”“周三”“本周”。

结构化结果至少包含：

```json
{
  "event_type": "PHONE_CALL",
  "date": "2026-07-22",
  "start_time": "10:00",
  "end_time": "10:30",
  "timezone": "Asia/Shanghai",
  "duration_minutes": 30,
  "location": null,
  "confidence": 0.95,
  "source_text": "明天上午十点可以聊一下吗"
}
```

相对时间必须结合消息接收时间和用户时区解析，并保留原始文本。日期、时间或时区存在歧义时不得假定已确认。

## 3. 默认时长和缓冲

在对方未说明时长时使用以下默认值：

- 电话沟通：30 分钟。
- 视频面试：60 分钟。
- 技术面试：90 分钟。
- 现场面试：面试时长加往返通勤时间。
- 所有事件默认前后各预留 15 分钟。

默认值仅用于冲突分析和建议，不代表对外承诺。

## 4. 日历冲突判断

查询范围应考虑：

- 已存在且标记为忙碌的会议。
- 全天事件。
- 用户工作时间和不可用时段。
- 用户手动设置的临时忙碌状态。
- 面试前准备和面试后缓冲。
- 现场面试往返通勤时间。
- 不同时区事件的统一换算。

暂定规则：标记为 `FREE` 的日历事件不构成冲突，`BUSY/TENTATIVE/OUT_OF_OFFICE` 构成冲突。该口径需在接入具体日历服务前确认。

## 5. 明确时间且无冲突

系统必须：

1. 先检查电话是否至少 `ROUGH_MATCH`，面试是否达到 `FULL_MATCH`；不足时先澄清岗位，
   不创建接受该邀请的确认任务。
2. 查询用户日历及不可用配置。
3. 计算包含缓冲的时间段是否冲突。
4. 创建时间确认任务，不直接回复招聘方。
5. 展示公司、职位、资格成熟度、沟通类型、日期、时间、时区、时长和冲突结论。
6. 提供建议回复。
7. 用户确认后才允许发送。
8. 用户可以选择确认后是否创建日历事件。

建议回复可以是：

```text
这个时间我可以，感谢安排。请问是电话沟通、视频会议还是其他形式？
```

## 6. 明确时间且有冲突

系统必须：

1. 标记原时间冲突并展示冲突类型，不泄露无关日程详情。
2. 在用户工作时间和可用规则内查询候选时间。
3. 生成两个或三个备选时间。
4. 生成换时间回复草稿。
5. 在用户确认或修改后再发送。

任何由系统提出的具体备选时间都属于必须确认内容。

## 7. 时间不明确

若对方只询问某天或某个宽泛时段是否方便，系统不得自行选择并直接承诺具体时间。

处理顺序：

1. 解析可确定的日期范围和事件类型。
2. 查询用户可用时间。
3. 生成候选时间或澄清问题。
4. 创建人工确认任务。
5. 用户确认后发送。

日期本身也不明确时，优先生成澄清草稿，而不是猜测日期。

## 8. 现场面试

现场面试除通用规则外还必须考虑：

- 面试地址是否明确。
- 出发地和交通方式是否已配置。
- 往返通勤时长。
- 额外准备时间。
- 用户是否接受该城市的现场面试。

地址或通勤信息不足时，系统不得声称不存在冲突，应提示冲突判断不完整并请求用户确认。

## 9. 确认与日历写入

- 时间确认和日历写入是两个独立授权动作。
- 用户确认对外回复不代表自动同意写入日历。
- 创建日历事件必须在对外时间已确认后执行，或由用户在同一确认操作中明确勾选授权。
- 对方后续变更时间时，原事件不得静默覆盖，应创建新的变更确认任务。
- 原时间冲突时只能选择服务端已检查的候选时间；候选时间尚未获得招聘方确认前不得
  创建日历事件。
- 取消或改期必须保存原事件关联和审计记录。
- 在发送前再次检查冲突，避免确认期间日历发生变化。
- 时间确认任务必须保存 `calendar_checked_at`、日历快照版本和 `expires_at`。发送前快照过期或日历版本变化时必须重新检查；出现新冲突时退回 `PENDING_APPROVAL`，不得沿用旧批准直接发送。

## 10. 时间确认卡片

至少展示：

- 平台、公司、职位和招聘人。
- 当前资格成熟度及支持该成熟度的岗位信息。
- 事件类型。
- 原始邀请文本。
- 解析后的日期、时间、时区和预计时长。
- 日历冲突状态和检查时间。
- 建议回复及备选时间。
- 是否创建或更新日历事件。
- 解析置信度和风险提示。

## 11. 异常与安全降级

- 日历不可用：不得声称时间空闲，创建“无法检查日历”的人工确认任务。
- 解析置信度不足：生成澄清草稿，不自动选择时间。
- 时区不明：明确展示时区待确认。
- 日历数据过期：发送前重新查询。
- 并发邀请占用同一时间：按最新日历状态重新判断，不以旧缓存批准。
- 任何错误都不得绕过用户确认要求。

时间回复执行结果无法确认时遵循通用动作状态 `OUTCOME_UNKNOWN`：先回读招聘对话确认是否已发送，不得直接重试。页面或登录异常时，将平台会话标记为 `SESSION_AUTH_REQUIRED`、`SESSION_PAGE_CHANGED`、`SESSION_TARGET_MISMATCH` 或 `SESSION_PAUSED`，并停止所有写操作。

## 12. 配置与默认口径

- `TENTATIVE` 默认视为冲突。
- 工作时间、午休、不可用时段、默认时长、前后缓冲和确认有效期均由用户配置，系统提供安全默认值。
- 现场面试通勤时间在接入地图服务前由用户手动设置；信息不足时不得声称无冲突。
- 日历事件默认不创建，必须单独授权或在同一确认卡片中明确勾选。
- 招聘方未说明时区时，只有双方职位场景均明确位于中国境内才可推断为 `Asia/Shanghai`，并必须显示风险提示；其他情况要求确认时区。
- 无论任何配置，日历空闲都不能绕过具体时间的用户确认。

## 13. 当前实现说明

- 默认使用本地假日历事件验证只读查询、冲突和授权写入流程；模拟空闲不代表真实空闲。
- 日历供应商可配置。Mac 默认使用 Apple Calendar，忙闲检查遍历系统日历但
  只返回开始和结束时间，不向业务层传递标题或内容；用户明确授权后才向配置的目标日历
  写入事件，并使用稳定标记防止重复创建。
- Google Calendar 仍可选，通过 FreeBusy 读取忙碌区间并在独立授权后写入事件；
  `MOCK` 仅用于自动测试。
- `CALENDAR_PROVIDER=APPLE` 时，macOS 权限未授予、非 Mac 环境、目标写入日历不存在或
  Calendar 调用失败，状态统一为 `UNAVAILABLE`。
- `CALENDAR_PROVIDER=GOOGLE` 但 OAuth 访问令牌缺失、过期、网络失败或响应无效时，
  日历状态为 `UNAVAILABLE`，不得回退到本地空日历并声称可用。
- 新邀请、改期或形式变化只有先通过当前资格门禁，才会替代同一对话中尚未完成的旧
  排期任务；不符合资格的新消息不能取消有效旧任务。旧任务保留审计，不静默覆盖。
  用户拒绝后任务进入 `CANCELLED`。
- 周末、配置工作时间外、午休以及包含缓冲后越过可用时段均视为冲突。
- 支持明确年月日、月日、明天、后天、本周/下周星期及常用中文时间表达；无法可靠解析时进入澄清流程。
- 配置保存在 `scheduling_preferences`，未配置时读取 `config/scheduling-policy.json` 的安全默认值。
- 真实地图通勤尚未接入；现场面试未配置通勤时间时状态为 `INCOMPLETE`，不得声称无冲突。

## 14. 排期识别和审计约束

- 只有明确电话、通话、语音或面试表达，并同时包含可解析日期和时间，才创建时间确认任务；
  “沟通一下、交流一下、聊聊”属于普通消息。
- 明确电话或面试但缺少具体时间时只生成普通澄清回复，不进入面试确认页。
- 无效日期或时间返回结构化模糊风险，不允许未捕获异常污染消息状态。
- 每次日历检查保存 provider、查询起止、时区、查询时间、快照哈希和脱敏忙碌摘要。
- 排期回复来源固定为 `HUMAN`；日历创建结果无法确认时进入
  `CALENDAR_OUTCOME_UNKNOWN`，不得直接再次创建。
