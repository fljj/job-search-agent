# 电话、面试与日历策略

## 1. 适用范围

本文是电话沟通、视频面试、技术面试、现场面试、具体时间建议和日历冲突判断的权威规则。

核心原则：系统可以识别、查询、分析和生成建议，但任何包含具体沟通或面试时间的对外回复都必须先取得用户确认。

## 2. 时间邀请识别

系统应识别：

- 对方提出明确日期和时间。
- 对方提出日期但未给具体时间。
- 对方询问用户可用时间。
- 电话、视频、技术或现场面试类型。
- 预计时长和地点。
- 相对日期，例如“明天”“周三”“本周”。

结构化结果至少包含：

```json
{
  "event_type": "PHONE_CALL",
  "date": "2026-07-22",
  "start_time": "10:00",
  "end_time": "10:30",
  "timezone": "Asia/Shanghai",
  "duration_minutes": 30,
  "location": null,
  "confidence": 0.95,
  "source_text": "明天上午十点可以聊一下吗"
}
```

相对时间必须结合消息接收时间和用户时区解析，并保留原始文本。日期、时间或时区存在歧义时不得假定已确认。

## 3. 默认时长和缓冲

在对方未说明时长时使用以下默认值：

- 电话沟通：30 分钟。
- 视频面试：60 分钟。
- 技术面试：90 分钟。
- 现场面试：面试时长加往返通勤时间。
- 所有事件默认前后各预留 15 分钟。

默认值仅用于冲突分析和建议，不代表对外承诺。

## 4. 日历冲突判断

查询范围应考虑：

- 已存在且标记为忙碌的会议。
- 全天事件。
- 用户工作时间和不可用时段。
- 用户手动设置的临时忙碌状态。
- 面试前准备和面试后缓冲。
- 现场面试往返通勤时间。
- 不同时区事件的统一换算。

暂定规则：标记为 `FREE` 的日历事件不构成冲突，`BUSY/TENTATIVE/OUT_OF_OFFICE` 构成冲突。该口径需在接入具体日历服务前确认。

## 5. 明确时间且无冲突

系统必须：

1. 查询用户日历及不可用配置。
2. 计算包含缓冲的时间段是否冲突。
3. 创建时间确认任务，不直接回复招聘方。
4. 展示公司、职位、沟通类型、日期、时间、时区、时长和冲突结论。
5. 提供建议回复。
6. 用户确认后才允许发送。
7. 用户可以选择确认后是否创建日历事件。

建议回复可以是：

```text
这个时间我可以，感谢安排。请问是电话沟通、视频会议还是其他形式？
```

## 6. 明确时间且有冲突

系统必须：

1. 标记原时间冲突并展示冲突类型，不泄露无关日程详情。
2. 在用户工作时间和可用规则内查询候选时间。
3. 生成两个或三个备选时间。
4. 生成换时间回复草稿。
5. 在用户确认或修改后再发送。

任何由系统提出的具体备选时间都属于必须确认内容。

## 7. 时间不明确

若对方只询问某天或某个宽泛时段是否方便，系统不得自行选择并直接承诺具体时间。

处理顺序：

1. 解析可确定的日期范围和事件类型。
2. 查询用户可用时间。
3. 生成候选时间或澄清问题。
4. 创建人工确认任务。
5. 用户确认后发送。

日期本身也不明确时，优先生成澄清草稿，而不是猜测日期。

## 8. 现场面试

现场面试除通用规则外还必须考虑：

- 面试地址是否明确。
- 出发地和交通方式是否已配置。
- 往返通勤时长。
- 额外准备时间。
- 用户是否接受该城市的现场面试。

地址或通勤信息不足时，系统不得声称不存在冲突，应提示冲突判断不完整并请求用户确认。

## 9. 确认与日历写入

- 时间确认和日历写入是两个独立授权动作。
- 用户确认对外回复不代表自动同意写入日历。
- 创建日历事件必须在对外时间已确认后执行，或由用户在同一确认操作中明确勾选授权。
- 对方后续变更时间时，原事件不得静默覆盖，应创建新的变更确认任务。
- 取消或改期必须保存原事件关联和审计记录。
- 在发送前再次检查冲突，避免确认期间日历发生变化。
- 时间确认任务必须保存 `calendar_checked_at`、日历快照版本和 `expires_at`。发送前快照过期或日历版本变化时必须重新检查；出现新冲突时退回 `PENDING_APPROVAL`，不得沿用旧批准直接发送。

## 10. 时间确认卡片

至少展示：

- 平台、公司、职位和招聘人。
- 事件类型。
- 原始邀请文本。
- 解析后的日期、时间、时区和预计时长。
- 日历冲突状态和检查时间。
- 建议回复及备选时间。
- 是否创建或更新日历事件。
- 解析置信度和风险提示。

## 11. 异常与安全降级

- 日历不可用：不得声称时间空闲，创建“无法检查日历”的人工确认任务。
- 解析置信度不足：生成澄清草稿，不自动选择时间。
- 时区不明：明确展示时区待确认。
- 日历数据过期：发送前重新查询。
- 并发邀请占用同一时间：按最新日历状态重新判断，不以旧缓存批准。
- 任何错误都不得绕过用户确认要求。

时间回复执行结果无法确认时遵循通用动作状态 `OUTCOME_UNKNOWN`：先回读招聘对话确认是否已发送，不得直接重试。页面或登录异常时，将平台会话标记为 `SESSION_AUTH_REQUIRED`、`SESSION_PAGE_CHANGED`、`SESSION_TARGET_MISMATCH` 或 `SESSION_PAUSED`，并停止所有写操作。

## 12. 配置与默认口径

- `TENTATIVE` 默认视为冲突。
- 工作时间、午休、不可用时段、默认时长、前后缓冲和确认有效期均由用户配置，系统提供安全默认值。
- 现场面试通勤时间在接入地图服务前由用户手动设置；信息不足时不得声称无冲突。
- 日历事件默认不创建，必须单独授权或在同一确认卡片中明确勾选。
- 招聘方未说明时区时，只有双方职位场景均明确位于中国境内才可推断为 `Asia/Shanghai`，并必须显示风险提示；其他情况要求确认时区。
- 无论任何配置，日历空闲都不能绕过具体时间的用户确认。
