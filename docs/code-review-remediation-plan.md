## 1. 审查目标与范围

本次审查的目标不是继续修补单个现象，而是确认当前需求、文档、领域规则、状态机、
浏览器执行、数据库、API、前端和测试是否形成一致且可验证的闭环，并给出后续小步整改依据。

审查范围包括：

- 根目录 `AGENTS.md`、`README.md` 及 `docs/` 下全部项目文档；
- `apps/api`、`packages`、`adapters`、`scripts` 中的后端和 Worker 实现；
- `apps/web` 中的前端页面、状态展示和配置表单；
- 全部 Alembic 迁移及当前 ORM 模型；
- 单元测试、浏览器脱敏夹具测试和现有集成测试；
- 当前 Git 工作区和项目提供的 lint、类型检查、测试、构建命令。

本次共检查约 3.6 万行 Python、TypeScript 和 Markdown，包含 229 个 Python 文件、22 个
TypeScript/TSX 文件、原有 10 个 Markdown 文件和 34 个 Alembic 版本文件。创建本文前工作区为干净状态。

### 1.1 限制

代码审查和自动测试不能从数学意义上“保证所有代码绝对正确”。当前结论基于静态检查、
领域规则交叉核对和脱敏测试。由于未配置 `TEST_DATABASE_URL`，9 个 PostgreSQL 集成测试被跳过；
本次也没有连接真实招聘网站、真实日历或真实 LLM，更没有执行任何外部写操作。

因此，只有完成本文 P0/P1 整改、补齐 PostgreSQL 集成验证和受控真实只读/写入验收后，才能重新
判断系统是否适合无人值守运行。

## 2. 总体结论

当前项目已经具备职位发现、硬性过滤、LLM 评分、入站沟通、动作队列、审计、幂等、日历和多平台
适配等主要模块，测试覆盖数量也较高。但是，系统目前仍不适合直接宣称“安全稳定地无人值守”：

1. 有些浏览器动作可以绕过统一策略引擎，安全开关和紧急停止并非对所有写操作都生效；
2. 动作执行状态和页面回读证据不够严格，可能留下永久 `EXECUTING`、错误
   `OUTCOME_UNKNOWN`，或把历史相同消息误认成本次发送成功；
3. 派生会话身份不足以授权写操作，存在同名招聘人或职位切换时选错会话的风险；
4. LLM 熔断当前会阻断本可由规则和知识库处理的消息，与 Reply Router 的目标冲突；
5. 消息、职位、终态和重试缺少统一、持久化且可恢复的处理语义，异常项目可能被无限重复处理；
6. 前端自动化设置表单可能用默认值覆盖已经生效的配置，这是直接影响安全边界的高风险问题；
7. 多份文档同时保留不同阶段的旧规则，已不能作为唯一可靠的实现依据；
8. 当前测试全部通过不代表这些风险不存在，因为多数问题属于跨事务、跨轮询和真实页面身份问题。

在 P0 问题修复和验证前，建议暂停真实平台自动写操作；只读发现、离线解析、测试夹具和人工查看
可以继续运行。

## 3. 必须先统一的业务不变量

后续修改不得继续围绕单个页面现象打补丁。应先把以下规则作为唯一验收基线：

1. 硬性排除必须先于 LLM；已确定硬性排除的职位不得调用 LLM，也不得主动沟通。
2. 主动招呼必须同时满足：无硬性排除、职位开放、分数不低于 80、模型建议沟通、策略和平台开关允许。
3. 入站消息不受主动招呼的 80 分门槛约束。对方明确索要简历或发出平台同意卡片时，在不存在
   明确诈骗、黑名单、地点等确定性阻断的前提下，可发送平台默认简历或同意卡片。
4. “提到了简历”不等于“明确索要简历”；“已看过简历”“简历不合适”等不得触发再次发送。
5. 到岗、薪资、地点、工作模式和知识库事实优先走 Rule/Knowledge，不得为这些问题调用 LLM。
6. 电话或面试的具体时间以及日历写入必须人工确认；普通交流意愿和联系方式交换不属于面试确认。
7. 任何外部写操作都必须通过统一策略判定、身份复核、幂等检查和审计，浏览器适配器不得自行授权。
8. 结果无法确认时进入 `OUTCOME_UNKNOWN`，先只读对账；没有观察到写入不等于可以立即重试。
9. 候选人或招聘方明确结束沟通后，会话进入持久化终态；只有明确的新业务消息或人工重开才恢复。
10. Worker“应该运行”、Worker“进程存活”和平台“页面可用”是三个不同状态，前端不得混为一谈。

## 4. 需求和文档冲突

### DOC-01：LLM 熔断边界互相矛盾（P0）

- `docs/product-requirements.md` 和 `docs/conversation-policy.md` 的 Reply Router 章节要求：LLM 不可用时，
  规则回复、知识库回复和明确简历请求仍可继续。
- `docs/conversation-policy.md` 第 14 节、`docs/architecture.md` 和 `README.md` 又规定：LLM 熔断暂停全部
  Agent 业务。
- 当前 Worker 实现采用“暂停全部业务”，因此到岗、薪资和平台原生同意卡片也会停止。

建议：明确采用“能力分区熔断”。全局探针仍然单飞，但只暂停依赖 LLM 的解析、评分和开放式回复；
确定性硬过滤、Rule/Knowledge 回复、平台同意卡片、只读对账和维护任务继续运行。若用户最终要求
任何 LLM 故障都全停，则应删除文档中的降级承诺和相关测试目标，不允许两套语义并存。

### DOC-02：频率限制已经删除，但文档仍有旧描述（P1）

`docs/product-requirements.md`、`docs/development-plan.md` 和迁移说明明确不再设置小时/每日限额；
`docs/conversation-policy.md`、`docs/data-model.md`、`docs/architecture.md` 和 `README.md` 仍出现“频率限制”、
“限额”或旧字段。应统一删除已失效的业务规则，但保留平台异常退避、幂等冷却和故障恢复节流；
这些可靠性机制不是业务投递限额。

### DOC-03：入站简历资格条件没有唯一口径（P0）

文档同时存在“入站明确索要就直接发送”“岗位大概匹配才发送”“方向冲突不得发送”等表述。
猎头会话中页面标题常是“猎头顾问”，当前实现可能因此判为 `JOB_DIRECTION_CONFLICT`，从而拒绝
原本允许的入站简历请求。

建议：把入站简历拆成两个确定性判断：

- 是否是明确、当前、肯定的索要动作；
- 是否存在已经证实的硬阻断事实。

缺少完整职位信息只应是 `UNKNOWN`，不能自动等同 `MISMATCH`；猎头身份和实际招聘岗位必须分开建模。

### DOC-04：阶段性历史和当前规范混在一起（P1）

`docs/development-plan.md` 长期追加了第一阶段到第二十阶段的历史描述，同时保留 60 分简历门槛、
确定性维度评分、灰度级别和旧验收基线。`docs/api-design.md` 仍写“第一阶段没有浏览器写操作”，
与当前系统不符。

建议：

- `development-plan.md` 只保留当前状态、未完成工作、顺序、验收标准；
- 已完成阶段移入单独历史记录，明确“仅供追溯，不是当前规范”；
- API、数据模型和架构文档只描述当前契约；
- 业务规则只在对应专项文档定义，其他文档使用链接，不复制另一套规则。

### DOC-05：文档承诺的审计字段与数据库不一致（P1）

`docs/data-model.md` 描述 `actor_id`、`action_id`、`policy_decision_id`、`request_id` 等结构化审计字段，
当前实体并未完整提供，部分关联仅存在于 JSON 元数据或 correlation 字符串中。

建议：以真实查询和追责需求决定最小结构化字段，创建向前迁移并保留历史数据；暂不需要的字段从文档
删除，不能继续写成已经存在。

### DOC-06：结构和命名存在重复、过时和遗漏（P2）

- `AGENTS.md` 项目概述只写 BOSS 和脉脉，遗漏已支持的 Telegram；
- `docs/architecture.md` 有重复章节编号；
- `docs/data-model.md` 有重复章节及错位编号；
- `docs/api-design.md` 部分后期 API 位于不对应的旧阶段章节；
- README 示例仍包含 `low_score_decline_enabled`、`auto_resume_min_score` 等遗留字段，并使用“限额”措辞。

应在功能整改完成后统一整理，避免先改文档后又因代码变化重复返工。

## 5. 代码审查问题

优先级定义：

- P0：可能造成错误外部写入、重复发送、安全策略绕过或无法恢复，必须先修复；
- P1：可能造成持续误判、漏处理、状态不可信或运维失控，应在恢复无人值守前修复；
- P2：影响性能、可维护性、展示准确性或长期演进，可在核心闭环稳定后处理。

### 5.1 P0：外部动作安全与状态机

#### CR-001：平台同意卡片绕过统一策略引擎

位置：`apps/api/app/services/message_discovery_service.py` 的 `_queue_platform_consents`。

现状：服务直接创建 `APPROVED/AUTO` 动作，未统一调用自动化有效配置和策略引擎。全局紧急停止、
平台开关、策略开关以及简历自动发送开关不能保证对这些动作生效。

修改方案：所有浏览器写动作统一经过一个公开的动作授权入口；输入包含用户、平台、策略、职位、会话、
动作类型和证据快照，统一返回 `ALLOW_AUTO`、`REQUIRE_CONFIRMATION` 或 `DENY`。消息发现服务只生成
意图，不得直接把动作标为已批准。

验收：关闭任意一层开关或启用紧急停止时，三类同意卡片均不能进入可执行状态；审计记录包含最终
策略决策及原因码。

#### CR-002：动作异常可永久停留在 `EXECUTING`

位置：`apps/api/app/services/action_service.py` 的 `execute_action`。

现状：动作和 attempt 先提交为执行中，再生成命令、调用外部执行器和结束动作。中间任一步骤抛异常，
直接 API 或调度路径可能留下持久化 `EXECUTING`；外部已成功但最终数据库提交失败时也没有可靠恢复语义。

修改方案：定义明确的执行阶段和异常映射：

1. 外部写入前失败 → `FAILED_RETRYABLE` 或 `FAILED_FINAL`；
2. 已开始外部写入但无可靠证据 → `OUTCOME_UNKNOWN`；
3. 成功回读 → `SUCCEEDED`；
4. 每个阶段都在独立、短事务中更新 attempt 和审计；
5. Worker 启动时回收超时 `EXECUTING`，根据 attempt 的“是否开始写入”标记决定失败或对账。

验收：对命令构建、外部执行、回读和最终提交分别故障注入，不得留下无租约的永久 `EXECUTING`，
也不得自动重复未知写入。

#### CR-003：未发生写入也可能被标记为 `OUTCOME_UNKNOWN`

位置：`adapters/browser/playwright_actions.py` 的回复执行流程。

现状：输入框填入内容后就设置 `performed=True`。随后找不到发送按钮时，系统会把“仅填写、未点击”
判成写入结果未知，导致会话和平台被不必要地阻塞。

修改方案：把 `prepared`、`write_started` 和 `observed` 分开。只有执行发送点击、回车发送或同意按钮
点击后才可进入未知结果；发送前失败应是明确的前置失败。

验收：发送按钮缺失、控件不唯一、输入失败均不得产生 `OUTCOME_UNKNOWN`；点击后网络中断必须产生
`OUTCOME_UNKNOWN`。

#### CR-004：回读可能用历史相同消息误判本次成功

位置：`adapters/browser/playwright_actions.py` 的发送确认和 `observe`。

现状：通过页面中是否存在包含目标文本的出站消息判断成功。若历史上发送过相同模板，旧消息可以被
当成本次新发送的证据。

修改方案：写入前记录会话身份、最后一条平台消息 ID、消息数或稳定时间戳基线；写入后只接受基线之后
新增的、方向为出站且内容精确规范化匹配的消息。证据中保存新消息的稳定外部 ID。

验收：同一文本历史存在时不误报成功；新消息出现时可确认；无法区分新旧时进入未知而非成功。

#### CR-005：部分 BOSS 写操作无法自动对账

位置：`adapters/browser/playwright_actions.py` 的 `observe`。

现状：BOSS 附件简历、平台默认招呼和部分同意卡片返回 `RECONCILIATION_NOT_SUPPORTED`。这些动作进入
未知后只能长期暂停或人工处理。

修改方案：为每类真实动作定义只读、动作特定的成功证据，例如新出站简历卡片、联系方式交换状态、
地点卡片已接受状态、平台生成的新招呼消息。没有可靠证据的动作必须默认禁止自动重试。

验收：每种可自动执行的动作都有成功、明确未发生和仍未知三个夹具用例；未知动作可在页面恢复后
完成对账。

#### CR-006：派生会话 ID 不足以授权写操作

位置：`adapters/browser/playwright_actions.py` 的 `_conversation_key_matches`、
`_reply_target_matches` 和 `_open_approved_conversation`。

现状：当期望 ID 以 `derived:` 开头时，任意实际 ID 都可能通过第一层检查；回复目标主要核对招聘人和
岗位标题，未完整核对公司。仅有一个同名招聘人候选项时可能先点入错误会话。

修改方案：

- 优先提取并持久化平台稳定会话 ID；
- 派生 ID 只能用于发现去重，不能单独授权写入；
- 降级匹配必须同时精确核对平台、招聘人、公司、岗位及最新消息证据；
- 任一字段缺失或多个候选时停止写入，不进行试探性点击。

验收：同名招聘人、同公司多岗位、岗位切换和虚拟列表复用场景均不能选错会话。

#### CR-007：BOSS 简历发送仍使用高风险的 Playwright 附加路径

位置：`adapters/browser/playwright_actions.py` 的 `execute`。

现状：招呼、回复和部分卡片已使用原生 CDP，但简历动作仍通过 Playwright `connect_over_cdp`。项目已有
真实页面因附加、重载或上下文管理出现崩溃/关闭的历史，且架构文档也承认此风险。

修改方案：真实 BOSS 简历发送统一使用已有的原生 CDP 会话管理和身份复核；Playwright 保留给脱敏
夹具和离线适配测试。不要通过“永不关闭标签页”掩盖生命周期问题。

验收：发送简历前后原有消息页、职位页和登录状态保持不变；执行器只关闭自己明确拥有的临时目标。

#### CR-008：自动化设置表单可能用默认值覆盖线上配置

位置：`apps/web/src/pages/AutomationPage.tsx`。

现状：页面读取了作用域设置，但表单以固定 `initialValues` 初始化，没有在选择作用域或加载完成时可靠
回填当前值。用户保存一个字段时，其他字段可能被默认值覆盖；部分后端配置字段甚至不在表单模型中。

修改方案：按选中作用域加载完整配置并 `setFieldsValue`；提交时采用有版本号的完整 PUT，或只提交显式
修改字段的 PATCH；显示当前继承值、覆盖值和最终有效值。保存时增加版本冲突保护。

验收：逐一修改单个开关不会改变其他开关；切换作用域不串值；并发更新返回冲突而不是静默覆盖。

### 5.2 P1：消息、职位、LLM 与调度逻辑

#### CR-009：LLM 熔断阻断 Rule/Knowledge 和明确卡片动作

位置：`scripts/run_agent_worker.py` 主循环、`apps/api/app/services/agent_service.py`。

现状：用户级 LLM 熔断打开后，Worker 跳过整轮业务；每次 run tick 也会先构造 LLM。无需模型的到岗、
薪资、地点、工作模式、知识库回复和平台原生卡片无法工作。

修改方案：按 DOC-01 的最终决定拆分无 LLM 队列和 LLM 队列。探针成功只恢复 LLM 能力，不修改原本的
平台暂停、登录异常或人工暂停状态。对账、租约回收和日志保留任务不能被 LLM 熔断跳过。

验收：模拟限流时到岗问题、地点卡片和明确简历请求仍按规则完成；开放式消息进入等待 LLM 状态且不
重复建草稿；探针恢复后只处理到期项目。

#### CR-010：LLM 故障被错误转换为人工确认任务

位置：`apps/api/app/services/conversation_service.py` 的 `_llm_failure_handoff` 和草稿持久化流程。

现状：Rule/Knowledge 无法处理时，LLM 故障会产生 `REQUIRE_CONFIRMATION/HUMAN` 草稿。这样普通消息也会
进入面试确认式人工任务，违反“仅具体电话/面试时间确认”的产品边界。

修改方案：增加 `WAITING_FOR_LLM` 或通用待处理状态，不创建动作批准任务；只有用户明确选择人工编辑，
或消息本身属于规定的高风险确认范围，才使用 `HUMAN` 来源。

验收：LLM 超时不会出现在面试确认页，不会生成可发送动作；恢复后可继续原消息且只有一个草稿。

#### CR-011：失败消息可能每轮无限重试

位置：`apps/api/app/services/agent_service.py` 的消息处理异常分支。

现状：部分 `ValueError`、资源缺失和结构错误只增加运行失败计数，原消息仍保持待处理，下一轮会再次
进入相同路径。一个坏消息可以长期消耗 CPU、日志和 LLM。

修改方案：为消息处理增加持久化状态、错误码、尝试次数、`retry_at` 和隔离状态；按错误类型决定立即
终止、退避或等待外部条件。修复数据后允许人工重放，但不得默认无限重试。

验收：同一确定性坏消息只处理一次并进入隔离；暂时 LLM 故障按统一熔断处理；重启 Worker 不丢失状态。

#### CR-012：动作前置错误的无限重试范围过宽

位置：动作分发和 Worker 的 `DISPATCH_PREWRITE_ERROR` 重试逻辑。

现状：通用前置错误可能每 60 秒无限重试，选择器错误、数据错误和临时页面未就绪没有区分。

修改方案：使用类型化错误：页面暂未就绪可退避，身份不一致和控件歧义直接暂停，配置/数据错误隔离，
LLM 故障进入统一熔断。每类错误配置明确的自动重试条件，而非一个宽泛白名单。

验收：永久错误不循环；临时错误按到期时间单飞；相同动作任一时刻只有一个有效 attempt。

#### CR-013：回退消息 ID 不稳定，可能重复回复或漏掉合法消息

位置：`adapters/browser/extractor.py` 的消息提取。

现状：缺少平台消息 ID 时使用“会话 ID + 列表索引 + 内容”生成哈希。虚拟列表排序变化会把同一消息
识别为新消息；相同位置和内容的合法新消息又可能被误去重。缺少时间时以扫描当前时间补齐也会放大变化。

修改方案：优先获取平台稳定 ID；回退指纹使用稳定会话、方向、平台显示时间和规范化内容，不使用列表
索引。无法可靠区分的新入站消息可以入库观察，但不得自动写回，直到身份和消息基线可确认。

验收：虚拟列表重排不产生重复消息；相同文本在不同平台时间可分别入库；模糊回退不会授权自动回复。

#### CR-014：列表提取采用“一项坏、整页停”

位置：`adapters/browser/extractor.py` 的职位和消息列表提取。

现状：一个广告、懒加载项或缺少字段的卡片可使整个列表返回页面结构变化；空列表也会直接按结构失败。
这会导致 `JOB_DISCOVERY_UNAVAILABLE` 或 `MESSAGE_DISCOVERY_UNAVAILABLE` 反复出现。

修改方案：区分 `LOADING`、合法 `EMPTY`、单项无效和选择器整体失效；无效单项跳过并记录脱敏诊断，
只有核心容器不存在或无任何可识别项时才暂停。设置有限的页面就绪等待，不刷新页面。

验收：夹具混入广告、占位骨架和一个残缺卡片时仍能提取其他有效项；真正 DOM 变更才暂停。

#### CR-015：终态推导会被更早的拒绝文本污染

位置：`apps/api/app/services/message_discovery_service.py` 的 `_terminal_state_from_messages`。

现状：从当前加载到的消息倒序搜索拒绝关键字，只要后来没有命中有限的重开短语，就可能用更早的
“不合适”把已经开始新一轮业务的会话再次结束。

修改方案：持久化终态事件的消息 ID和发生时间，只检查最后一段未归档对话；新职位、招聘方明确重开或
用户人工重开创建新 episode。终态会话轮询时只比较最后消息 ID，不反复打开详情。

验收：历史拒绝 + 新岗位邀请不会被旧文本结束；双方已结束且无新消息时不再打开或回复。

#### CR-016：职位方向预筛仍依赖正向标题枚举

位置：职位发现服务和 Telegram Worker 的 `is_potentially_relevant_title` 使用点。

现状：标题未命中 Java、后端等正向枚举时不会打开 JD。这样“银行系统研发”“AI 应用开发”等可能
符合候选人经历的岗位会被漏掉，而负向枚举又无法穷举所有无关岗位。

修改方案：预筛改为三态：

- 明确相关：打开一次；
- 明确无关：基于强领域证据跳过且不调用 LLM；
- 不确定：打开一次读取 JD，再把确定性方向结论和内容指纹持久化。

同一内容指纹已经判定无关后不再打开；JD 变化后才重新评估。

验收：结构总工、园林、纯客服等强无关标题不调用 LLM；银行系统研发等不确定标题会读取一次 JD；
同一无关职位不会重复打开。

#### CR-017：未知工作模式被推断为现场办公

位置：`adapters/browser/extractor.py` 的职位规范化。

现状：工作模式未知但存在地点时，会直接推断为 `ONSITE`。远程岗位也可能展示公司注册地或招聘地，
因此可能触发错误地点硬排除。

修改方案：没有明确“现场/坐班/到岗”证据时保持 `UNKNOWN`；远程、混合和现场只能由明确页面字段或
JD 证据决定。硬过滤不得把 UNKNOWN 当成 ONSITE。

验收：远程岗位带城市标签不被误排；明确济南现场按策略判断；未知模式给出风险而非虚构结论。

#### CR-018：相同外部职位变化后不会更新

位置：`apps/api/app/services/job_service.py` 的 `import_job`。

现状：外部 ID 或内容哈希重复就返回 `DUPLICATE`。职位薪资、JD、状态发生变化时，当前记录和评分可能
继续使用旧数据，不符合文档中的原始观察和版本化要求。

修改方案：外部 ID 用于职位身份，内容哈希用于版本身份。相同外部 ID、新内容哈希时创建不可变观察版本，
更新当前快照并使旧评分过期；完全相同内容才是幂等重复。

验收：薪资、JD、开放状态任一变化都会生成新版本并重新执行硬过滤；相同快照重复导入不产生新版本。

#### CR-019：猎头身份被当作岗位方向

位置：入站资格判定和消息职位绑定流程。

现状：页面显示的“猎头顾问”可能被作为职位标题，进而产生 `JOB_DIRECTION_CONFLICT/MISMATCH`，阻断对方
明确索要简历。猎头身份不得被当作岗位方向，也不再单独阻止主动沟通或入站处理。

修改方案：增加招聘方角色/来源字段，职位未知时资格保持 `UNKNOWN`；“不主动联系猎头”只约束主动动作，
不自动推导职位不匹配。拿到实际 JD 后再更新职位资格。

验收：猎头索要简历不会因“猎头顾问”标题被拒绝；明确不合适的实际岗位仍可被硬阻断。

#### CR-020：简历意图识别过宽

位置：`packages/conversation_agent` 的意图关键词及入站简历动作创建。

现状：只要包含“简历”或“附件”就可能被识别成简历请求。“看过简历”“简历不合适”“简历里没看到”
不应触发发送，却可能进入相同路径。

修改方案：建立独立、确定性的 `explicit_resume_request`：要求请求动词、当前时态和肯定语义，或平台原生
卡片证据；先处理拒绝、已查看和过去事件。LLM 可以辅助开放文本分类，但不能覆盖否定规则。

验收：覆盖索要、已看、拒绝、附件问题、再次索要和平台卡片；只有明确请求创建简历动作。

#### CR-021：薪资规则漏识别自然问法

位置：`packages/conversation_agent/rules/salary.py`。

现状：“您目前期望的是多少哇”没有显式“薪资”二字，可能漏过 Rule Router 并交给 LLM，导致回复技术
经历而没有回答问题。

修改方案：补充保守的语境模式，并结合当前会话职位的工作模式读取对应薪资策略；工作模式未知时明确
分别说明远程/本地口径，或先询问岗位模式。不得编造单一数字。

验收：直接问、口语问、上下文追问和非薪资“期望”语句均有测试；命中时 LLM 调用次数为零。

#### CR-022：历史记忆可能永久压制合理追问

位置：`packages/conversation_agent/memory.py`。

现状：曾经询问或确认过的话题会被长期视为已处理，即使招聘方更新了岗位、薪资或工作模式，也可能
删除本轮必要问题；部分主题关键词过宽。

修改方案：只抑制同一 conversation episode 中仍然有效且已有回答的问题；保存问题、回答、关联消息和
事实版本。职位或事实变化后允许重新确认，避免仅靠宽泛关键词去重。

验收：相同未回答问题不重复问；对方给出新薪资/新职位后可以重新确认；不同问题不会因“Java”等词误合并。

#### CR-023：电话/面试识别过于敏感

位置：调度意图路由和 `packages/scheduling` 的邀请解析。

现状：“希望和你交流一下”等一般沟通可能进入电话/面试确认；事件类型在缺少明确证据时默认电话。
日期组合也可能构造无效日期并抛异常。

修改方案：只有明确电话/视频/现场面试且包含具体候选时间，才创建时间确认；泛交流保持普通回复。
日期解析必须返回结构化校验错误，不得抛出未捕获异常；缺失年份和跨月日期需有明确时区规则。

验收：泛交流不进入面试确认页；明确电话但无时间只进行普通澄清；无效日期安全失败且不污染消息状态。

#### CR-024：日历和人工草稿审计不完整

位置：调度服务和日历检查实体。

现状：日历冲突快照可能只持久化空数组，无法证明实际查询范围和来源；调度生成草稿未必统一标记
`reply_source=HUMAN`；外部日历事件创建失败后的对账边界不完整。

修改方案：保存 provider、查询区间、时区、查询时间和脱敏冲突摘要；人工确认草稿统一记录来源；
日历创建使用外部幂等键，并实现读取对账。确认过期后必须重新查冲突。

验收：同一确认重复提交只创建一个事件；日历写入未知时不重复创建；审计可还原当时的忙闲依据。

#### CR-025：LLM 解析结果复用没有绑定模型和提示版本

位置：`apps/api/app/services/score_service.py` 和职位解析记录。

现状：最新 `parser_type=LLM` 的解析可能被复用，但没有完整绑定 provider、model、prompt/schema 版本和
调用记录。切换智谱/千问或模型后可能继续使用旧解析。

修改方案：解析指纹至少包含 JD 内容哈希、provider、model、prompt/schema 版本和候选资料/策略事实版本；
复用必须精确匹配。解析记录关联 LLM invocation，评分继续保留独立规则版本。

验收：切换模型、提示版本或 JD 后会重新解析；相同指纹保持幂等；历史评分可定位实际模型来源。

#### CR-026：自动化有效规则通过修改已验证对象合并

位置：自动化服务的 `_effective_rules` 及其跨模块调用。

现状：代码在 Pydantic 模型创建后修改字段，默认未启用赋值再验证；多层工作时间合并可能产生
`start >= end` 等初始化时不会出现的非法组合。私有函数还被脚本和其他服务直接引用。

修改方案：先合并原始字典，再一次性构造并验证最终模型；将其变成公开、单一入口，所有动作授权使用
同一结果。非法跨层组合保存时即拒绝。

验收：全局、平台、策略三层组合有参数化测试；非法时间窗不能产生有效配置。

### 5.3 P1/P2：运行状态、数据库、查询和前端

#### CR-027：Run、Worker 和平台可用状态混为一谈（P1）

位置：Worker 心跳、Agent Run API 和前端总览。

现状：`AgentRun.RUNNING` 表示期望运行，不证明 Worker 进程仍存活；前端还可能使用单个全局
`workerRunning` 推导各平台状态，因此没有 Worker 时仍显示 BOSS/脉脉/Telegram 运行中。

修改方案：分别展示：

- Desired state：用户配置的运行/暂停；
- Worker lease：进程实例、心跳和过期时间；
- Platform readiness：每个平台页面、登录和最近成功扫描；
- Capability state：LLM、日历和执行器是否可用。

验收：无 Worker、Worker STALE、一个平台页面丢失和 LLM 熔断时均显示准确且互不覆盖。

#### CR-028：职位发现批量打开详情页并在慢操作期间保留（P1）

位置：BOSS 职位发现适配和 Worker 编排。

现状：可能先打开一批详情目标，再进行慢速 LLM 评分，临时标签长期存在，增加浏览器资源和用户页面被
干扰的概率。

修改方案：一次只读取一个详情快照，立即关闭执行器明确拥有的临时详情目标，再进行 LLM 处理；用户原有
消息页和职位列表页永不由详情读取流程关闭。

验收：批量 100 职位时临时目标数量有上界；LLM 超时不会遗留详情标签；列表和消息页不被关闭或刷新。

#### CR-029：页面恢复可能重复创建标签，缺少统一所有权（P1）

位置：消息/职位 `ensure_*_page` 和浏览器会话管理。

现状：恢复失败时不同模块可各自创建页面，缺少统一的目标注册、所有权和就绪状态，可能出现多个重复
消息页、职位页，或关闭非本模块创建的目标。

修改方案：建立轻量会话协调器，记录平台页面角色、target ID、是否由 Agent 创建和最后核验时间；只复用
唯一已登录页面，缺失时明确暂停并由“重新连接”触发一次恢复。禁止通过频繁刷新维持消息发现。

验收：重复恢复请求幂等；用户关闭页面后只补建一个；执行器只关闭自己拥有的临时详情页。

#### CR-030：列表 API 存在内存分页和 N+1 查询（P2）

位置：`job_service.list_jobs`、会话列表、动作列表和审计差异查询。

现状：职位列表先加载全部记录、逐项查询最新评分/沟通，再在 Python 过滤分页；会话列表虽已 SQL 分页，
仍逐条获取草稿、决策和动作。数据增长后会变慢，且动作接口有未分页路径。

修改方案：使用最新记录子查询或窗口函数，在数据库完成过滤、稳定排序、计数和分页；所有列表接口设置
明确最大页大小。排序键最后统一追加主键，避免同时间数据跨页抖动。

验收：固定数据量下查询数为常数级；翻页无重复/遗漏；10 万级模拟数据下响应时间满足约定基线。

#### CR-031：总览把当前页数量当作全局指标（P1）

位置：`apps/web` 总览页面及对应列表 API 使用。

现状：前端获取默认第一页后直接计算总数或状态分布，职位、消息和动作增多后会展示局部数据，却让用户
误以为是全局统计。

修改方案：新增独立聚合概览 API，返回数据库计算的总数、待处理数、失败数和时间窗口；列表页只负责
当前页。页面注明统计时间并定期轻量轮询 API，不刷新招聘网站。

验收：超过两页的数据仍显示正确总数；列表排序稳定；新数据在约定时间内自动更新。

#### CR-032：数据库状态约束和关系不足（P1）

位置：`apps/api/app/models/entities.py` 和 Alembic 迁移。

现状：多种状态以普通字符串保存，Worker 内部写入可绕过 Pydantic 枚举；动作与草稿的唯一关系、删除和
保留策略不完全一致。审计关联依赖 JSON，难以可靠查询。

修改方案：对核心状态增加数据库 CHECK 或原生 enum 约束；为动作/草稿关系定义唯一约束和明确 `ondelete`；
补齐最小审计外键/请求 ID。所有迁移只向前添加或回填，不压平、不删除已应用历史迁移。

验收：非法状态通过 ORM 直接写入也被数据库拒绝；删除/保留测试不会留下悬空动作或丢失必要审计。

#### CR-033：部分配置字段已经失效或语义重叠（P1）

位置：AutomationSettings、策略文档、API schema 和前端系统设置。

现状：存在 `low_score_decline_enabled`、`auto_resume_min_score` 等历史字段；自动回复置信度在多个配置对象
中重叠，部分值没有实际参与授权；`has_verified_facts` 等字段使用链路不完整。

修改方案：先建立“配置字段 → 读取位置 → 决策结果 → 测试”清单。没有读取者或已被新规则替代的字段标为
deprecated，停止在 UI 展示和新 API 写入；完成数据迁移和兼容期后再删除。不可直接根据名称猜测并删除。

验收：每个保留配置都有唯一语义和至少一个行为测试；前端展示值等于服务端最终有效值。

#### CR-034：动作类型和状态逻辑散落在字符串中（P1）

位置：动作队列实体、策略引擎、消息发现、执行器和前端映射。

现状：卡片同意、推荐同意等动作未完全纳入统一 `ActionType`，各模块使用字符串集合判断，新增动作容易
漏掉策略、对账、审计或中文展示。

修改方案：建立唯一动作类型枚举和动作能力表，至少声明：是否外部写入、需要的策略开关、幂等键组成、
执行器、对账器和中文标签。状态转换由单一服务验证。

验收：新增或保留的每个动作类型都有授权、执行、对账、审计和展示测试；未知类型不能执行。

#### CR-035：候选人资料和策略编辑能力不完整（P2）

位置：候选人资料页、策略页和对应 API。

现状：后端存在部分更新接口，但前端更偏向追加资料；策略主要通过原始 JSON 编辑，容易提交非法或互相
矛盾的字段。知识库停用、事实来源和当前生效版本的可见性不足。

修改方案：保留高级 JSON 作为调试入口，增加与 schema 对齐的最小表单和冲突提示；候选资料支持编辑、
停用和查看事实来源，不提供会破坏历史审计的物理删除。

验收：用户可编辑已存在资料和策略；非法地点/薪资/工作模式组合在提交前后都被拒绝；历史评分仍引用
原事实版本。

#### CR-036：本地 API 缺少明确的访问边界（P1）

位置：FastAPI 启动配置、固定用户上下文和 CORS 设置。

现状：系统按单用户本地应用设计，但缺少认证；如果 API 绑定局域网地址，任何可访问客户端都可能调用
启动、配置和动作接口。CORS 不是认证机制。

修改方案：当前阶段至少强制默认绑定 `127.0.0.1` 并在启动时拒绝无显式安全配置的公网/局域网绑定；
如确需跨设备访问，增加本地访问令牌和服务端权限校验。前端隐藏按钮不能作为权限边界。

验收：默认端口仅本机可达；非本机绑定必须显式启用认证；无凭证的写 API 被拒绝。

#### CR-037：前端仍展示内部代码和失效配置（P2）

位置：职位中心、消息中心、自动化和调度页面。

现状：部分未知状态回退显示英文枚举/原因码；失效配置仍可编辑；`RESUME`、`MISMATCH` 等曾造成业务
含义误解。

修改方案：服务端返回稳定业务码，前端集中映射中文标签和解释；未知码显示“未知状态（代码）”并记录
诊断，不静默伪装。删除确认无效的配置入口，动作展示使用“准备/已发送默认简历”等完整短语。

验收：核心状态和原因码均有中文快照测试；用户能区分资格、动作建议和实际执行结果。

#### CR-038：前端生产包已接近单块上限（P2）

位置：`apps/web` 路由和构建配置。

现状：生产构建成功，但主 chunk 约 506.88 kB，超过 Vite 的 500 kB 提示阈值。

修改方案：核心逻辑稳定后按页面路由做 `lazy` 拆分，不通过单纯提高告警阈值掩盖问题。

验收：首屏 chunk 低于当前告警阈值，页面行为和测试不变。
