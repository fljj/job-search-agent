# 职位评分规则

## 1. 规则目标

评分引擎使用大模型结合求职策略、结构化 JD 和候选人可信资料计算职位匹配度。程序不再使用固定公式替代模型的语义判断，但必须：

- 在调用模型前确定性执行全部硬性排除。
- 使用固定的七维满分、结构化输出模型和证据引用约束模型。
- 校验各维度范围、维度之和、总分、等级和主动沟通建议。
- 拒绝模型虚构候选人技能、经历或解除硬性排除的输出。
- 在模型不可用或输出非法时停止新评分，以及依赖本次评分的主动招呼等自动写操作；
  不依赖评分的确定性入站安全路径以 `docs/conversation-policy.md` 为准。

每次评分应记录：职位解析版本、候选人资料版本、策略版本、评分提示词版本、模型供应商、模型名称、模型响应 ID、评分规则版本和必要输入快照。不得记录 API Key。

## 2. 处理顺序

```text
校验职位和策略
→ 规范化职位字段
→ 使用确定性解析器提取硬性规则所需字段
→ 程序执行全部硬性排除规则；命中时保存排除结果并停止，不调用 LLM
→ 未命中时解析完整 JD，并在正式评分前再次执行硬性排除规则
→ 将策略、JD、候选人可信事实和评分量表提交给 LLM
→ LLM 返回七个维度分数、证据、理由、风险和主动沟通建议
→ 程序校验结构、范围、求和、证据和阈值
→ 程序计算等级并形成最终动作约束
→ 保存评分明细
```

硬性排除优先于 LLM 评分。命中后保存 `FILTERED_OUT`、排除原因及输入快照，七个维度
标记为“未评分”，不调用 LLM 解析、评分或招呼语生成。职位中心应显示
“硬性排除（未AI评分）”，不能把该结果解释为模型给出的低分。

只有确定性预筛通过的职位才进入完整 JD 解析和 LLM 评分。若完整解析补充的信息新命中
硬性规则，则停止后续 LLM 评分；此前的解析调用仍保留审计记录。

## 3. 输出模型

- `total_score`：整数，范围 `0–100`。
- `grade`：`A/B/C`，只由总分决定。
- `eligibility`：`ELIGIBLE/FILTERED_OUT`。
- `hard_rejected`：是否命中至少一条硬性排除。
- `rejection_reasons`：全部排除规则编码、说明和证据。
- `dimension_scores`：各维度得分、满分及明细。
- `match_reasons`：只基于已验证事实生成。
- `risk_notes`：信息缺失、推断、冲突和不确定项。
- `llm_recommends_proactive_contact`：模型是否建议主动沟通。
- `llm_contact_reason`：模型建议或不建议主动沟通的依据。
- `automation_eligible`：程序综合硬性排除、职位状态、总分和模型建议后的结果。

等级边界：

```text
总分 >= 70       → A
60 <= 总分 < 70  → B
总分 < 60        → C
```

等级与动作阈值相互独立：

- `total_score < 80`：不得根据职位列表主动招呼。
- `total_score >= 80`：只有模型同时建议主动沟通，且全部确定性约束通过时，才允许自动招呼。
- 策略配置 `headhunter_score_cap` 且可靠识别为猎头岗位时，程序在 LLM 输出校验后按固定维度顺序扣减并将总分封顶；该值最高为 79，因此猎头岗位可以保留和回复，但不能主动招呼。
- A 级仍从 70 分开始，因此 70–79 分属于“A 级但不主动沟通”，不得把等级直接等同于自动化权限。

### 3.1 入站对话不生成伪评分

BOSS、猎聘等支持普通入站消息的平台中，由招聘方先发起的消息可能只有岗位名称或部分岗位信息。首次
回复、澄清和对方明确索要简历时可以不执行完整的 100 分评分。系统不得为了复用
60/80 分门槛而人为补全缺失字段、生成虚假总分或把简化判断保存为正式 `JobScore`。

入站对话产生独立的资格成熟度判断：

- `UNKNOWN`：信息不足，可以澄清或按明确请求发送简历；
- `ROUGH_MATCH`：大体符合，可以继续沟通并推进电话邀约；
- `FULL_MATCH`：关键信息充分且符合，可以推进面试；
- `MISMATCH`：存在明确冲突，礼貌婉拒。

脉脉系统推荐卡片在此基础上额外产生
`ACCEPT_AND_SEND_PROFILE/REJECT_RECOMMENDATION/DENY`。该规则不改变 A/B/C、
80 分主动招呼和猎头封顶规则。取得足够 JD 信息后应进入完整解析和 100 分评分，但
评分用于展示、比较和主动招呼资格，不反向撤销此前合规的入站回复或简历发送。

## 4. 硬性排除规则

规则应返回稳定编码，不得只返回自由文本。

| 编码 | 条件 |
|---|---|
| `WORK_MODE_DISABLED` | 策略未启用职位对应工作模式 |
| `ONSITE_LOCATION_NOT_ALLOWED` | Onsite 地点不在允许城市 |
| `HYBRID_LOCATION_NOT_ALLOWED` | Hybrid 地点不在允许城市 |
| `TITLE_EXCLUDED` | 职位标题命中排除词 |
| `REQUIRED_CORE_SKILL_MISSING` | JD 明确要求的核心硬门槛技能全部缺失 |
| `SALARY_BELOW_MINIMUM` | 可可靠比较的薪资上限仍低于策略最低值 |
| `INDUSTRY_EXCLUDED` | 命中排除行业 |
| `COMPANY_BLACKLISTED` | 公司规范化名称命中策略黑名单 |
| `OUTSOURCING_NOT_ACCEPTED` | 明确为纯人力外包且策略禁止外包 |
| `PART_TIME_NOT_ACCEPTED` | 明确为兼职且策略不接受兼职 |
| `HEADHUNTER_NOT_ACCEPTED` | 可可靠识别为猎头且策略禁止猎头 |
| `INTERNSHIP_POSITION` | 明确为实习岗位 |
| `JUNIOR_POSITION` | 明确为策略不接受的初级岗位 |
| `FULL_TIME_BACHELOR_REQUIRED` | JD 明确要求全日制/统招本科，候选人本科不是全日制，且策略启用该排除规则 |

约束：

- Remote 不因公司所在地触发地点排除。
- 工作模式未知不触发地点硬排除，只产生风险提示。
- `accept_part_time=true` 时，兼职岗位不因公司所在地或平台推断的 Onsite 模式直接排除。
  只有 JD 明确要求现场、线下、驻场或坐班时，才继续执行 Onsite/Hybrid 地点硬性规则；
  未明确办公方式时按未知模式评分并在沟通中确认，不得擅自推断为远程。
- 薪资面议、薪资缺失、币种无法换算或税前税后不明确时，不触发薪资硬排除。
- `SALARY_BELOW_MINIMUM` 只有在规范化后的职位薪资上限低于最低值时触发；区间下限低、上限仍满足时只降低薪资分并提示区间风险。
- 核心技能排除必须基于策略明确标记的硬门槛技能，不得把所有 `required_skills` 自动视为硬门槛。
- 公司黑名单采用规范化后的精确匹配，避免模糊匹配误杀。
- 只有命中可配置的“全日制本科/统招本科”明确表述才触发学历形式排除；“本科及以上”
  或学历信息缺失不得推断为全日制要求。候选人学历形式未知时也不得硬性排除。

重复导入、职位关闭或过期、已经招呼、已经沟通和已经发送简历属于导入幂等、职位生命周期或动作阻断，不是职位匹配硬性排除。它们不得改变分数、等级或 `eligibility`。关闭或过期职位通过 `source_status` 和策略相关的 `effective_job_status` 表达，禁止动作的原因通过 `action_blockers` 返回。

猎头分数封顶不是硬性排除：`accept_headhunter=true` 时职位仍为 `ELIGIBLE`；命中封顶后增加
`HEADHUNTER_PROACTIVE_CONTACT_BLOCKED` 动作阻断和风险说明，并保证七维分数之和仍等于封顶后的总分。

## 5. LLM 评分约束、总分与取整

| 维度 | 满分 |
|---|---:|
| 岗位方向 | 15 |
| 技术栈 | 25 |
| 工作经历 | 15 |
| 工作模式与地点 | 15 |
| 薪资 | 15 |
| 行业 | 10 |
| 管理经验或岗位级别 | 5 |
| 总分 | 100 |

模型必须对每个维度返回 `score`、`max_score`、`reason` 和引用的条目级输入事实标识。
程序在调用模型前为候选人技能、行业经历、策略规则、解析字段和职位标量生成
`evidence:<sha256>` 证据目录。标识由来源路径和规范化 JSON 值生成，因此列表重排不
改变标识；目录条目同时记录允许引用的维度。

模型只能逐字返回当前 `input.evidence_items` 中的完整标识。集合不为空时必须引用实际
使用的具体条目，不得只引用 `candidate.skills` 等集合路径。程序拒绝以下结果：

- 引用当前输入目录不存在的标识；
- 在错误维度引用证据；
- 重复引用同一证据；
- 当前策略、候选人资料或解析结果变化后继续使用旧目录；
- 任一维度没有证据引用。

各维度可使用小数，结果最多保留两位；总分由程序对模型返回的七个维度原始分求和后
四舍五入得到。模型返回的 `total_score` 只用于一致性校验，两者不一致时拒绝本次结果，
不得静默修正后继续自动沟通。

以下量表是模型评分提示词和输出校验契约，不再由程序按关键词机械计算。模型可以在维度范围内进行语义判断，但必须解释分值并引用输入证据。

## 6. 岗位方向：15 分

岗位方向匹配由模型结合职位标题、JD 职责、必须技能、优先技能、策略目标方向、排除词和
岗位级别综合判断。数据库和 API 为兼容现有数据仍使用 `title` 作为维度编码，但前端应展示
为“岗位方向”。

- 标题命中排除词：`0` 分，并触发 `TITLE_EXCLUDED`。
- 精确或规范化后命中包含标题：`15` 分。
- 标题包含目标技术方向和岗位族：`12` 分。
- 仅命中岗位族，例如“后端开发”但未注明 Java：`9` 分。
- 标题使用业务名称或宽泛名称，但 JD 职责和技能能够证明属于目标岗位方向：`5–12` 分，
  根据核心职责和主技术栈的匹配程度确定。
- 方向相关但级别或职责不完全一致：`5–8` 分。
- 无有效匹配：`0` 分。

不得仅因标题没有出现 `Java`、`后端` 等策略关键词直接给 `0` 分。例如“银行系统研发”
标题未注明技术语言，但正文明确包含后端系统设计、Java 模块或与候选人目标方向相关的
核心职责时，必须基于正文评估岗位方向。反之，正文明确为财务、销售、运营等无关职责时
仍应给 `0` 分。

打开详情前先执行可配置的目标方向粗匹配：标题命中目标技术、岗位族、业务系统建设方向
或策略中的包含规则时，才继续执行明显无关词检查并读取 JD；没有任何目标方向证据时，
标记 `TITLE_DIRECTION_NOT_RELEVANT`，不打开详情、不导入职位，也不调用大模型。该门控是
低成本的正向相关性判断，不要求标题必须出现 `Java`，例如“银行系统研发”“风控系统建设
负责人”可由“研发”“系统建设”等方向证据进入 JD 分析。

通过目标方向粗匹配后，再执行有限的高置信度明显无关词排除。业务领域词或宽泛职能词
（例如“风控”“分析师”“系统”“应用”）不得单独作为明显无关依据；策略包含规则优先
放行存在歧义但明确属于目标方向的标题，例如“Java 开发（客服系统）”。明显无关关键词
不承担完整岗位分类，新增无关职业无需穷举到该列表。

职位标题排除规则仍由策略配置并只对标题执行。模型必须说明使用的策略项及 JD 证据；
程序另外执行标题硬性排除，不允许模型以正文语义匹配分解除排除。

## 7. 技术栈：25 分

输入分为：

- JD 必须技能 `required_skills`。
- JD 加分技能 `preferred_skills`。
- 候选人具有可信证据的技能。

默认权重：必须技能占 `80%`，加分技能占 `20%`。必须技能为空时，加分技能最多贡献 `12.5` 分，避免只有加分项的 JD 获得技术栈满分；加分技能为空时，权重全部转移给必须技能。两者均为空时得 `12.5` 分并提示 JD 技能信息不足。

```text
required_ratio = 已匹配必须技能权重 / 必须技能总权重
preferred_ratio = 已匹配加分技能权重 / 加分技能总权重
两类技能均存在：skill_score = 25 × (0.8 × required_ratio + 0.2 × preferred_ratio)
仅必须技能存在：skill_score = 25 × required_ratio
仅加分技能存在：skill_score = 12.5 × preferred_ratio
```

模型可以识别常见技能别名和语义相关技能，但必须同时返回规范化名称和原文证据。程序只接受来自 JD 和候选人资料的证据，不接受模型新增的候选人技能。

候选人没有证据的技能按未匹配处理。加分技能缺失不会触发硬性排除。

## 8. 工作经历：15 分

由年限匹配和经历特征组成：

- 相关年限：最多 `9` 分。
- 核心系统或复杂业务经验：最多 `3` 分。
- 与职位相关的行业或项目类型经验：最多 `3` 分。

年限规则：

- JD 未提供年限：`6` 分并提示信息不足。
- 候选人年限达到要求：`9` 分。
- 低于要求不超过 1 年：`7` 分。
- 低于要求 1–3 年：`4` 分。
- 低于要求超过 3 年：`1` 分。

经历特征必须来自候选人资料中的结构化事实。管理和架构能力主要在第 12 节计分，不得在本维度重复给满额；仅当其构成 JD 核心业务经历时才可作为相关经历证据。

## 9. 工作模式与地点：15 分

- Remote 已启用：`15` 分，不限制公司所在地。
- Onsite 已启用且地点被允许：`15` 分。
- Hybrid 已启用且地点被允许：默认 `13` 分；策略可在 `12–15` 中配置。
- 工作模式未知：`8` 分，并提示需要确认模式和地点。
- 工作模式禁用或地点不允许：`0` 分，并触发对应硬性排除。

地点比较应先做行政区划别名规范化，例如“济南”和“济南市”。无法可靠解析的地点不得按允许地点处理。

## 10. 薪资：15 分

### 10.1 规范化

用于比较的统一单位为税前人民币月薪 K，并保留原始薪资：

- 月薪直接使用职位区间。
- 年薪按薪数换算；薪数缺失时当前建议按 12 薪估算并产生风险提示。
- 奖金不明确时不计入保证薪资。
- 税后薪资不直接转换为税前薪资，按信息不确定处理。
- 外币只有在存在带版本的配置汇率时才换算。

### 10.2 计分

薪资计分阶梯属于策略数据，每种工作模式独立配置，不写死在评分代码中。区间可采用固定分或线性插值。

默认示例：

Remote：

- `>= 40K`：15 分。
- `35K–39K`：10–14 分。
- `30K–34K`：5–9 分。
- `< 30K`：0–4 分。
- 面议或无法规范化：8 分。

济南 Onsite：

- `>= 15K`：15 分。
- `13K–14K`：9–13 分。
- `10K–12K`：3–8 分。
- `< 10K`：0–2 分。
- 面议或无法规范化：8 分。

职位为薪资区间时，使用区间中点计分，同时按区间上限判断是否低于最低接受值。若区间跨越最低值，产生“薪资下限低于期望”的风险提示。

## 11. 行业：10 分

行业分由策略中的行业规则决定：

- 排除行业：`0` 分，并触发 `INDUSTRY_EXCLUDED`。
- 优先行业：策略配置 `8–10` 分。
- 可接受行业：策略配置 `3–8` 分。
- 未配置或无法识别：默认 `4` 分，并提示行业信息不足。

每个行业在同一策略中只能属于一种类型。多标签职位命中排除行业时，排除优先；否则取最高匹配分。

## 12. 管理经验或岗位级别：5 分

- JD 明确要求管理且候选人管理经验满足：`3` 分。
- JD 明确要求架构或技术规划且候选人具有证据：`2` 分。
- 两者均要求且均满足：`5` 分。
- JD 不要求管理或架构，且岗位级别与候选人匹配：默认 `2.5` 分。
- 要求存在但候选人没有相应证据：对应部分 `0` 分并产生风险提示。
- 岗位明显低于策略接受级别：`0` 分；配置为不可接受的初级岗位时同时硬性排除。

## 13. 匹配理由与风险提示

模型必须基于结构化输入生成评分证据，例如：

```json
{
  "dimension": "skills",
  "matched": ["Java", "Spring Boot", "Kafka"],
  "missing_required": ["Kubernetes"],
  "score": 20
}
```

理由只能依据输入事实，不得增加候选人事实。模型不可用、超时或输出校验失败时，本次评分状态为 `FAILED`，不得退回旧的确定性公式生成一个看似有效的新分数。

必须提示的风险包括：

- 工作模式、地点、行业或薪资缺失。
- 薪数、币种换算或税前税后属性不确定。
- 必须技能部分缺失。
- 相关年限低于要求。
- 岗位级别可能不匹配。
- JD 解析置信度不足或规则与大模型结果冲突。

## 14. 主动沟通决策

模型在评分结果中返回：

```json
{
  "llm_recommends_proactive_contact": true,
  "llm_contact_reason": "核心技术和工作地点符合策略，主要风险为薪资区间需要进一步确认"
}
```

最终是否主动沟通由程序按以下顺序决定：

1. 模型结果通过结构和证据校验。
2. 未命中任何硬性排除。
3. 职位处于可沟通状态且未过期。
4. `total_score >= 80`。
5. `llm_recommends_proactive_contact = true`。
6. 自动化开关、频率、去重、页面身份和平台状态全部通过。

任何一步失败都不能主动沟通。模型可以建议“不主动沟通”；模型不能建议绕过 80 分门槛。

### 14.1 多策略选择

- Agent 主动发现职位时，按启动任务绑定的单一策略评分和决策，不在运行中自动切换策略。
- 招聘方主动建立但尚未绑定策略的对话，对所有已启用且关联当前候选人资料的策略分别评分。
- 多策略结果不得平均；选择“未硬性排除且总分最高”的结果绑定对话，分数相同时选择策略优先级更高者。
- 如果所有策略均硬性排除，则记录全部策略结果，选择优先级最高策略的可公开原因用于婉拒，不暴露公司黑名单或内部排除标签。
- 对话绑定策略后，只有用户修改绑定或策略停用才重新选择；策略、JD、候选人资料或提示词版本变化只触发同一策略重新评分。

## 15. 测试要求

- 使用固定模型响应测试每个维度的 0 分、满分、越界、缺失和非法证据。
- 覆盖合法条目、列表重排、集合中不存在的值、跨维度引用、重复引用、过期目录和历史
  输入快照恢复。
- 覆盖维度求和不一致、未知维度、重复维度、非数字和超长理由。
- 覆盖 `59/60/69/70/79/80/100` 的等级及动作边界。
- 验证维度总和与总分一致且不超过 100。
- 每条硬性排除至少包含命中用例和不应命中的反例。
- 多条排除同时命中时返回全部原因且顺序稳定。
- 验证模型可以决定维度分和主动沟通建议，但不可修改等级算法、硬性排除和 80 分门槛。
- 验证模型超时、限流、空响应、非 JSON、非法证据和供应商错误时不会产生外部写操作。
- 使用模拟 HTTP 响应测试智谱和千问适配器；默认测试不得依赖真实 API Key 或产生费用。

## 16. 模型供应商与默认口径

- 当前默认供应商为智谱 GLM-5.2；千问作为可配置兼容供应商。两者均通过 OpenAI
  兼容的 Chat Completions 接口和 JSON 结构化输出接入。
- 当前评分契约为 `llm:1.2.0` / `job-score-v11`；版本升级必须进入评分指纹，不能复用
  旧提示词或集合级证据评分。
- 供应商、基础地址、模型名称、超时和重试次数必须配置化；API Key 只从环境变量读取。
- 领域层依赖统一 `LLMProvider` 接口，不依赖供应商 SDK；切换供应商不得修改评分、
  对话和策略领域规则。
- 网络失败最多自动重试一次；评分 JSON 已返回但结构校验失败时，允许携带精简校验错误追加
  一次结构纠错请求。限流和服务端错误应记录并暂停本轮动作，不得触发业务写操作。
- 相同输入版本、提示词版本、供应商和模型参数生成评分指纹；重复请求返回已有有效结果。

- 不接入实时外币汇率，只使用策略中带版本的固定汇率；没有可用汇率时按未知薪资处理。
- 年薪未注明薪数时按 12 薪估算，并产生明确风险提示。
- 技能默认等权，硬门槛技能由策略中的受控列表配置；当前不支持任意技能权重编辑。
- Hybrid 地点分默认 13 分，策略允许在 12–15 分内配置。
- 初级岗位识别使用可配置的受控词表；只有可靠命中且策略不接受该级别时才硬性排除。
- A/B/C 的 60 和 70 分边界保持不变；自动招呼最低分固定为 80。入站对话是否婉拒由
  明确不匹配证据决定，不再由低于 60 分单独触发。

LLM JD 解析使用独立输入指纹，包含 JD 内容哈希、供应商、模型、解析提示版本、结构版本
以及当前候选资料/启用策略版本。解析记录关联实际 `llm_invocation`；任一版本变化必须重新
解析，不能按“最新一条 LLM 解析”直接复用。

## 17. 职位发现预筛

标题预筛输出 `RELEVANT/IRRELEVANT/UNKNOWN`。它只用于避免明显无关职位消耗 LLM：

- `IRRELEVANT`：有充分的非目标岗位证据，可跳过详情和评分；
- `RELEVANT`：标题已有目标方向证据，继续读取 JD；
- `UNKNOWN`：标题不足以判断，必须读取一次 JD，不能按无关处理。

工作模式未知不等于现场办公，不能据此触发地点硬排除。职位正文版本变化后应产生新的职位
观察与评分输入，旧版本结果不得冒充当前版本。
