# 职位沟通决策规则

## 1. 目标

系统不再计算七维分数、总分、A/B/C 等级或 60/70/80 分门槛。职位处理分为两层：

1. 程序执行确定性硬性排除；
2. 通过硬性排除后，LLM 结合精简 JD、候选人可信履历和策略，判断是否值得沟通。

最终决策只有：

- `CONTACT`：建议沟通；
- `SKIP`：不建议沟通；
- `REVIEW`：信息不足，需要后续补充或人工查看；
- `FILTERED_OUT`：程序命中硬性排除，未调用沟通决策模型。

## 2. 执行顺序

```text
读取职位卡片
→ 明显无关标题预筛（只在证据充分时跳过详情）
→ 规则解析 JD
→ 完整 JD 方向证据门禁
→ 程序执行硬性排除
→ 命中：保存 FILTERED_OUT，不调用 LLM
→ 未命中：必要时执行一次 LLM 结构化解析，并再次执行硬性排除
→ 向 LLM 发送精简决策输入
→ 校验 CONTACT / SKIP / REVIEW 输出
→ 保存决策、理由、匹配依据、不确定项和输入版本
→ 策略引擎决定是否允许主动沟通
```

## 3. 硬性排除

硬性排除由程序执行，LLM 无权解除。包括：

- 公司黑名单；
- 策略明确排除的岗位方向或行业；
- 标题不确定时可读取一次详情；若标题、职责和技能均不存在策略方向或候选人技能证据，按 `JOB_DIRECTION_CONFLICT` 排除；
- 已明确的工作模式或现场地点不允许；
- 已明确的薪资上限低于策略最低值；
- 不接受外包、实习、兼职或猎头且 JD 明确属于对应类型；
- 明确要求全日制本科，而候选人可信资料表明本科不是全日制且策略启用此规则；
- 明确低级职位或其他专项文档定义的硬性冲突；
- 职位已关闭或超过策略有效期时阻断自动动作。

信息未知不等于不符合。兼职岗位未明确要求异地现场办公时，不因公司所在地直接排除。

硬性排除记录必须保存规则码、可解释信息、证据和输入快照，并且 `llm_invocation_id` 为空。

## 4. LLM 决策输入

只发送判断是否值得沟通所需的信息：

- 职位标题、行业、地点、工作模式、薪资文本和招聘人类型；
- 必须/优先技能、年限、职级、管理和架构要求、精简职责；
- 候选人的核心技能、与 JD 相关的技能、年限、管理/架构/核心系统经验和行业经历；
- 目标方向、允许的工作模式和地点、薪资底线、行业偏好及兼职/外包/猎头配置。

不发送完整简历、完整策略对象、七维量表、证据目录或无关历史数据。候选人事实必须来自可信资料。

## 5. 输出与授权

模型输出结构：

```json
{
  "decision": "CONTACT",
  "confidence": 0.9,
  "matched_evidence": ["Java 与核心系统经验匹配"],
  "uncertainties": ["具体业务域需要确认"],
  "reason": "核心方向和主要能力满足，建议沟通"
}
```

程序校验枚举、置信度范围、字段长度和数量。只有同时满足以下条件才允许主动沟通：

- 决策为 `CONTACT`；
- 置信度不低于 `0.75`；
- 职位有效状态为 `OPEN`；
- 没有动作阻断；
- 自动招呼开关已启用；
- 招聘人不是被禁止主动联系的猎头。

`SKIP` 和 `REVIEW` 不创建主动招呼。入站消息、明确索要简历和平台同意卡片按
`docs/conversation-policy.md` 处理，不以主动职位决策门槛阻断。

## 6. 失败、幂等和审计

- 模型未配置、认证失败、限流、超时或服务异常时进入统一 LLM 熔断；恢复探针通过前暂停依赖 LLM 的业务。
- 决策 JSON 结构非法时允许追加一次精简纠错请求；仍失败则按 LLM 失败处理，不伪造决策。
- 相同职位、解析、策略、候选人、决策版本、供应商、模型和提示版本生成相同指纹并复用结果。
- 显式重新决策必须提供幂等键。
- 保存模型供应商、模型、提示版本、Token 用量、延迟、策略/资料版本和必要输入快照，不保存 API Key。

## 7. 测试要求

- 每条硬性排除规则覆盖命中和不命中边界；
- 硬性排除命中时验证 LLM 调用次数为零；
- 验证 `CONTACT / SKIP / REVIEW` 和低置信度边界；
- 验证主动沟通只接受有效 `CONTACT`；
- 验证精简请求不包含完整简历、七维量表和无关证据；
- 验证指纹幂等、模型失败、结构化重试和熔断恢复。
