# 产品需求文档

## 1. 产品目标

开发一套面向 BOSS 直聘、脉脉和白名单 Telegram 招聘频道的无人值守求职 Agent，按多套求职策略自动发现、筛选、
评分和沟通职位，并根据对话证据发送简历。电话与面试具体时间、安全异常和平台验证
仍由用户处理。

系统应优先提高职位筛选和沟通效率，同时避免误投、误发、虚构经历、泄露隐私或未经确认替用户作出承诺。

## 2. 产品原则

- 自动闭环优先：职位发现、评分、主动沟通、普通回复和符合条件的简历发送默认自动化；电话和面试具体时间必须由用户确认。
- 事实优先：所有候选人信息必须来自可信知识来源，不得由大模型猜测。
- 规则可控：程序负责硬性排除、输入校验、分值上限、总分求和、等级和动作门槛；
  LLM 只在受控结构化契约内给出七个维度分及解释，不能绕过程序约束。
- 可解释：用户可以查看职位为何得分、为何被排除以及系统准备执行什么操作。
- 可暂停：用户可以全局关闭自动化，也可以单独暂停某个平台或某类动作。
- 平台合规：不规避验证码、滑块、设备识别或平台安全机制。

## 3. 用户与核心对象

第一版以单用户、单候选人资料运行，但数据模型应保留用户和候选人归属关系。

核心对象包括：

- 候选人资料：技能、经历、行业背景、管理经验和求职约束。
- 求职策略：职位方向、工作模式、地点、薪资、行业及黑名单规则。
- 职位：原始 JD、规范化字段、解析结果和来源标识。
- 评分结果：各维度分数、总分、等级、排除原因、匹配理由和风险提示。
- 对话：招聘方消息、意图、草稿、置信度和发送状态。
- 简历：多个网站内附件版本及其适用方向。
- 确认任务：等待用户批准、修改或拒绝的动作。
- 策略决策：针对具体动作输出自动允许、需要确认或拒绝，并保存命中规则。
- 日程请求：电话或面试邀请、冲突结果、候选时间和确认状态。
- 审计记录：系统分析、决策和执行结果。

## 4. 第一阶段范围：职位策略和评分

第一阶段不连接任何真实招聘网站，不读取真实会话，也不发送消息或简历。

### 4.1 求职策略

系统支持创建、查看、编辑、启用和停用多套独立策略。每套策略至少包含：

- 策略名称和启用状态。
- 包含及排除的职位名称。
- 可接受的岗位级别。
- `REMOTE`、`ONSITE`、`HYBRID` 和未知工作模式的独立规则。
- Onsite 和 Hybrid 的允许地点。
- 不同工作模式的最低薪资、期望薪资和计分阶梯。
- 优先行业、可接受行业和排除行业。
- 公司黑名单。
- 是否接受猎头、外包和兼职岗位。
- 职位允许的最大发布天数。

默认业务口径：

- Remote 职位不限制公司所在地。
- Onsite 职位仅接受策略明确配置的城市；默认示例为济南。
- Hybrid 独立启用并配置地点，不自动继承 Onsite 规则。
- 兼职是独立策略开关。接受兼职时，JD 明确要求现场办公的岗位仍受现场地点规则约束；
  JD 未明确办公方式时不得仅依据公司所在地硬性排除，应继续沟通确认。
- 工作模式未知时保留职位、降低确定性并提示待确认。

### 4.2 候选人评分资料

第一阶段需要维护评分所需的最小候选人资料：

- 总工作年限和相关技术年限。
- 已掌握技能及证据来源。
- 团队管理年限。
- 架构设计和核心系统经验。
- 已有行业经验。

该资料只服务于评分；用于自动回复的完整知识库在第二阶段建设。

### 4.3 模拟 JD 导入

支持单条和批量导入模拟职位，至少包含：

- 职位名称、公司和行业。
- 地点和工作模式。
- 薪资原文及可选结构化薪资字段。
- 职位描述。
- 发布时间和来源声明的职位状态。
- 模拟来源职位 ID。

系统应检测重复职位。优先使用“来源 + 来源职位 ID”去重；缺少来源职位 ID 时使用规范化内容哈希。

### 4.4 JD 结构化解析

系统从 JD 中提取：

- 必须技能和加分技能。
- 要求工作年限。
- 管理、架构和岗位级别要求。
- 工作模式和地点。
- 薪资范围、周期、薪数、币种及税前税后属性。
- 职责、行业、外包或实习等特征。

解析和语义评分由大模型完成，输出必须通过结构化校验。程序继续负责确定性硬性排除、分值范围与求和校验、版本记录和动作阈值约束。

### 4.5 职位评分与展示

系统按 `docs/scoring-rules.md` 先执行确定性硬性排除，再由大模型结合策略、JD 和候选人资料完成 100 分评分，并输出：

- 总分和 A/B/C 等级。
- 七个维度的得分及满分。
- 是否硬性排除及全部排除原因。
- 匹配理由。
- 风险和待确认事项。
- 使用的策略版本和评分规则版本。

硬性排除状态与等级分开表达。被排除职位仍可保留信息性分数，但不得进入可主动沟通队列。

系统还应区分三个互不替代的概念：

- `eligibility`：职位是否符合求职策略；
- `source_status`：招聘来源声明的开放、关闭或未知状态；
- `effective_job_status`：结合具体策略发布时间限制得出的开放、关闭、过期或未知状态；
- `action_blockers`：重复招呼、重复简历、页面变化等动作级阻断。

重复导入或已经沟通过不改变职位匹配分数，也不作为评分硬性排除；它们分别由导入幂等和动作权限处理。

### 4.6 第一阶段页面

- 策略列表和创建/编辑页面。
- 候选人评分资料页面。
- 模拟 JD 导入页面。
- 职位列表、筛选和评分详情页面。

职位列表支持按策略、等级、硬性排除状态和工作模式筛选。

## 5. 后续产品范围

后续阶段的具体顺序以 `docs/development-plan.md` 为准。

- 建立完整候选人知识库和多版本简历管理。
- 生成个性化招呼语并分析招聘方消息意图。
- 以只读方式接入用户已登录的招聘网站页面。
- 建立动作决策和审计数据；只有电话、面试具体时间和日历写操作进入人工确认。
- 在安全阈值内启用高匹配职位的常规自动沟通。
- 接入日历，识别电话和面试邀请，检查冲突并推荐时间。

自动沟通规则见 `docs/conversation-policy.md`，时间与日历规则见 `docs/scheduling-policy.md`。

以下小节描述当前确认后的目标范围，不代表代码已经完成；实际实现状态以 `docs/development-plan.md` 的“当前里程碑”为准。

### 5.1 第二阶段目标范围

- 管理带来源、敏感度、有效期和自动引用权限的候选人知识项；
- 管理网站内附件简历的名称、平台、适用方向和可用状态；
- 创建模拟对话并幂等导入招聘方消息；
- 识别多意图，基于已验证事实生成个性化招呼语和回复草稿；
- 计算可解释置信度，并输出 `ALLOW_AUTO/REQUIRE_CONFIRMATION/DENY` 决策；
- 除电话和面试具体时间外，回复不进入人工确认；缺少事实时使用保守口径，敏感信息自动拒绝披露，禁止虚构。

第二阶段不执行任何真实发送、简历上传、网站操作或日历排期。

### 5.2 第三阶段目标范围

- 使用 Playwright 连接用户手动登录的本机 Chromium CDP 会话；
- 分别使用 BOSS 直聘和脉脉只读适配器读取当前职位或对话页；
- 将受校验的职位、招聘人和消息幂等导入已有业务模型；
- 检测未登录、验证页、未支持页面、选择器失效和目标身份不一致；
- 保存结构化读取记录、状态、原因码和去除查询参数的页面证据引用。

第三阶段不提供点击发送、输入、上传、验证码处理、反检测或任何其他网站写操作。

### 5.3 第四阶段目标范围

- 展示时间类待确认内容、原因、置信度和风险，支持批准、修改后重新检查或拒绝；
- 招呼、普通回复、不匹配婉拒和简历发送可由 `ALLOW_AUTO` 进入安全执行链路；具体时间仍必须批准后单独触发；
- 执行前复核平台、公司、职位、招聘人、对话、内容和附件名；
- 仅允许选择已登记且平台中唯一匹配的附件简历，不上传文件；
- 通过幂等键、原子状态占用、尝试记录、简历去重和追加审计防止重复执行；
- 外部结果不明确时进入 `OUTCOME_UNKNOWN`，不允许盲目重试。

### 5.4 第五阶段目标范围

- 提供默认关闭的全局、平台和策略三级自动化配置，子级只能收紧上级权限；
- 对招呼、普通回复、不匹配婉拒和简历发送分别执行“模型建议 + 确定性约束”授权；
- 只有未命中硬性排除、职位开放、模型建议主动沟通且总分达到 80 分的职位才可自动招呼；
- 职位列表中的主动招呼必须使用最新有效评分，并严格执行 80 分门槛；
- BOSS、脉脉等平台中由招聘方先发起的消息允许在未完成正式评分时先进入沟通；
- 对方当前消息明确、肯定地索要简历时，只要没有已经证实的保险销售、完全无关岗位、
  黑名单、欺诈、重复发送、错误目标或附件不可用等确定性阻断，即可先发送当前平台
  登记的默认可用简历，不按职位标题、适用方向或评分二次匹配；仅提及简历、已经查看
  简历或表示简历不合适不属于索要；
- 沟通过程持续补全岗位、地点、工作模式、薪资和职责。发现明确不符合策略时自动礼貌
  婉拒；信息仍不足时继续澄清，不得伪造评分；
- 电话沟通在岗位大体符合后可以进入邀约流程；面试只有在岗位信息充分且确认符合后
  才能进入邀约流程。电话和面试具体时间仍必须确认；
- 敏感信息、无事实、硬性排除、非开放职位、重复发送和附件不可用采用自动拒绝、保守回复或停止动作的安全降级，不创建普通人工确认；
- JD 明确要求全日制/统招本科且候选人本科不是全日制时，可按策略硬性排除；招聘方主动
  询问学历性质时如实回复，未询问时不主动披露；
- 不设置小时或每日处理配额；页面或身份异常后暂停该平台自动化；
- 自动动作复用第四阶段的原子执行、发送指纹、结果回读和追加审计。
- 职位中心必须分别展示评分资格、主动沟通动作结果和会话是否已经建立；职位与消息中心
  通过 `job_id` 双向联动，发送前失败不得显示为已有沟通。

### 5.5 第六阶段目标范围

- 确定性识别电话、视频、技术和现场面试邀请，解析明确或相对日期时间；
- 使用用户时区、默认时长、前后缓冲、工作时间、午休及现场通勤配置检查冲突；
- 支持本地假日历事件导入和只读冲突检查，日历不可用时安全降级；
- 冲突或宽泛时间生成二至三个候选时间或澄清回复；
- 所有具体时间回复均创建人工确认任务，日历空闲也不会自动发送；
- 发送前检查日历快照，变化或过期后重新检查，新冲突退回待确认；
- 对外回复确认和创建日历事件使用独立授权，操作结果具备审计和幂等保护。

### 5.6 招聘方入站优先沟通与平台推荐

BOSS、脉脉等平台中，招聘方先发起的消息与职位列表中的 Agent 主动招呼采用不同权限
规则。100 分评分和 80 分门槛用于限制 Agent 主动联系，不用于阻止招聘方已经发起的
初步沟通。

入站消息处理原则：

- 可以在未完成正式评分时回复安全的岗位澄清问题；
- 对方当前消息明确、肯定地索要简历时，可以先发送平台内已登记的默认可用简历；
- 发送前仍必须排除已经证实的保险销售、完全无关岗位、公司黑名单、欺诈风险、错误
  目标、错误附件和重复发送；职位信息不足保持 `UNKNOWN`，不得仅因标题不完整或猎头
  身份推断为 `MISMATCH`；
- 后续持续收集岗位信息；发现地点、工作模式、薪资、行业、岗位方向或公司明确不满足
  策略时礼貌拒绝；
- 猎头身份不阻止回复其主动消息或按其明确请求发送简历，但 Agent 仍不得主动向猎头
  打招呼。

对话维护独立的资格成熟度：

- `UNKNOWN`：信息不足，允许澄清和按明确请求发送简历；
- `ROUGH_MATCH`：现有信息大体符合，允许继续沟通并推进电话邀约；
- `FULL_MATCH`：关键信息充分且符合，允许推进面试邀约；
- `MISMATCH`：存在明确冲突，礼貌拒绝并停止正常推进。

电话邀约只要求 `ROUGH_MATCH`，面试邀约必须达到 `FULL_MATCH`。二者的具体时间仍由
用户确认，日历空闲不能自动代替确认。

### 5.7 脉脉系统推荐快速处理

脉脉“系统推荐”消息属于平台已经提供岗位卡片和“同意/拒绝”操作的特殊入站场景，
不等同于 Agent 主动发现职位，也不要求在第一次操作前完成完整的 100 分评分。

系统应读取推荐卡片中当前可见的岗位名称、公司、招聘方身份、地点、薪资和职责摘要，
执行确定性的简化判断：

- 保险销售、保险代理、拉人头式销售或与候选人求职方向完全无关的岗位选择“拒绝”；
- 技术、研发、架构、Java/后端、AI/Vibe Coding、直播运营及其他大致相关岗位选择
  “同意”，使用脉脉平台自带能力直接投递平台资料和附件简历；
- 信息不足但没有明确负面证据时按“大致相关”处理，不因缺少完整 JD 单独拒绝；
- 猎头身份不阻止处理招聘方已经发起的系统推荐，但仍不得据此触发 Agent 主动招呼；
- 命中公司黑名单、排除行业、欺诈风险或敏感信息风险时仍必须拒绝。

“同意/拒绝”必须保存推荐卡片快照、简化判断结果、命中规则、目标招聘人和岗位、
执行结果及平台回读证据。同一推荐只能处理一次，结果不明确时进入 `OUTCOME_UNKNOWN`
并先对账，不得重复点击。

同意推荐后，对方后续真人回复进入上述入站优先沟通流程。系统继续补全 JD 和资格
成熟度；正式评分只用于展示和后续职位比较，不作为已经建立的入站对话继续沟通或
首次按请求发送简历的前置条件。

## 6. 非功能需求

### 6.1 安全

- 不保存招聘网站账号密码。
- 不破解验证码、滑块或规避平台风控。
- 不输出或记录无必要的敏感信息。
- 服务端必须再次校验用户确认状态，不能仅依赖前端。

### 6.2 可审计性

- 保存职位原始数据和结构化解析结果。
- 保存评分输入快照、策略版本及规则版本。
- 保存自动化决策、确认、执行结果和失败原因。
- 审计记录采用追加写，外部结果不明确时保留对账状态，不得盲目重试。

### 6.3 可用性

- 大模型不可用或输出校验失败时打开 LLM 能力熔断：不创建新评分、不主动招呼，也不
  处理依赖 LLM 的开放式回复；确定性硬过滤、Rule/Knowledge 回复、符合入站规则的
  明确简历请求、平台原生同意卡片、只读对账和维护任务继续运行。无法由这些渠道安全
  处理的普通消息进入等待 LLM 状态，不创建普通人工确认。电话和面试具体时间仍不得
  自动确认。
- 外部页面结构异常或目标身份不一致时，自动操作应安全停止。
- 批量导入时单条失败不应导致全部有效数据回滚。

## 7. 第一阶段验收标准

1. 可以创建、编辑、启用和停用多套策略。
2. Remote 北京职位不因公司所在地被排除。
3. 北京 Onsite 职位在仅允许济南的策略下被硬性排除。
4. 济南 Onsite 15K 职位获得满地点分和满薪资分。
5. Hybrid 能独立配置启用状态、允许城市和薪资规则。
6. 培训机构、禁用外包和黑名单公司能够被硬性排除。
7. 可以单条和批量导入模拟 JD，并识别重复职位。
8. 可以查看总分、七维分数、等级、理由、风险和排除证据。
9. `59/60/69/70/79/80/100` 的等级和主动招呼边界正确，入站动作不与分数错误耦合。
10. 大模型不可用或输出非法时不会产生新评分、主动招呼或其他依赖本次模型结果的外部
    写操作；确定性安全路径按第 6.3 节继续。
11. 大模型负责分值和沟通建议，但不能解除程序计算的硬性排除或绕过 80 分门槛。
12. 评分结构校验、硬性排除、动作授权和降级路径具有完整单元测试，API 具有关键集成测试。

## 8. 第一阶段默认决策

- 不接入实时外币汇率，只支持策略配置的固定汇率；未配置时按未知薪资处理。
- 年薪未注明薪数时按 12 薪估算，并产生“薪数为推断值”的风险提示。
- Hybrid 地点分默认 13 分，允许策略在 12–15 分内配置。
- 猎头只有在策略禁止且 JD 可可靠识别时才排除。
- 初级岗位使用可配置的受控默认词表；可靠命中且策略不接受该级别时才排除。
- 第一阶段不支持任意技能权重编辑，使用等权技能和受控核心技能列表。
