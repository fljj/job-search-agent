# 自动沟通与人工确认策略

## 1. 适用范围

本文定义第二阶段及后续阶段的：

- 个性化招呼语。
- 招聘方消息分析和自动回复。
- 候选人事实与敏感信息使用。
- 附件简历选择和发送。
- 人工确认队列。

电话、视频或现场面试的具体时间处理以 `scheduling-policy.md` 为唯一权威来源。

## 2. 基本原则

- 回复只能使用候选人知识库中的可信事实。
- 不存在可靠事实时不得猜测，应请求用户补充或使用安全占位回复。
- 发送前必须校验当前平台、公司、职位、招聘人和对话是否与任务一致。
- 同一招聘人、同一公司或高度相似职位应避免重复招呼和重复回复。
- 所有自动发送和人工确认操作均记录输入、决策、内容和结果。
- 用户可以全局或按平台关闭自动招呼、自动回复和自动发送简历。

## 3. 职位等级与首次沟通

评分资格状态优先于等级：任何 `FILTERED_OUT` 职位默认不得主动沟通或发送简历。

- A 级：在自动招呼开关、频率限制、去重和风险检查均通过时，可自动发送个性化招呼语。
- B 级：生成招呼语并默认进入人工确认队列；只有用户明确启用“60 分以上自动招呼”时才允许自动发送。
- C 级：默认不主动沟通、不发送简历；用户可以手动加入白名单后操作。

## 4. 个性化招呼语

招呼语至少使用：

- 职位名称和公司行业。
- JD 的核心职责和两到三个关键技能。
- 候选人与岗位最匹配的两到三个真实事实。
- 需要进一步确认的工作模式、团队或业务问题。

要求：

- 控制长度，避免堆砌全部技能。
- 不虚构项目、结果、技术或管理经验。
- 不包含身份证、家庭、银行等敏感信息。
- 不作薪资、到岗或入职承诺。
- 相似岗位的文本应有针对性差异，但不得为追求差异而改变事实。

## 5. 候选人知识库

知识项至少包含：

- `fact`：可引用事实。
- `source`：简历、用户输入或经确认资料。
- `allowed_for_auto_reply`：是否允许自动使用。
- `sensitivity`：普通、敏感或禁止使用。
- `verified_at`：最近确认时间。
- `valid_until`：可选有效期。

知识库覆盖：个人介绍、工作及项目经历、技术栈、管理经验、行业经验、学历、薪资期望、地点、远程要求、到岗时间、离职原因、不可回答事项和附件简历信息。

缺少明确事实时，默认回复草稿为：“这部分信息我需要确认一下，稍后回复您。”该草稿不得伪装成已确认事实。

## 6. 消息意图

至少支持：

```text
JOB_DETAIL
TECH_STACK
WORK_EXPERIENCE
PROJECT_EXPERIENCE
MANAGEMENT_EXPERIENCE
SALARY
LOCATION
REMOTE_POLICY
ARRIVAL_DATE
RESUME_REQUEST
PHONE_CALL
INTERVIEW_INVITATION
INTERVIEW_TIME
COMPANY_INTRODUCTION
UNCLEAR
SENSITIVE
```

消息可能同时具有多个意图。时间相关意图识别后必须交给排期策略处理，不能由普通回复策略直接承诺。

## 7. 回复置信度与权限

置信度只用于普通问题；命中敏感或必须确认规则时，无论置信度多高都不得自动发送。

- `confidence >= 0.90`：普通问题可自动发送。
- `0.75 <= confidence < 0.90`：生成草稿，进入人工确认。
- `confidence < 0.75`：不得自动回复，创建人工处理任务。

置信度应综合：意图识别、知识命中、事实新鲜度、上下文完整性和内容风险，不能直接使用大模型自报概率作为唯一依据。

## 8. 允许自动回复的普通问题

在知识库事实明确且允许自动使用时，可以回复：

- Java、Spring Boot、Spring Cloud 等技术经验。
- 数据库、Redis、Kafka、Docker、Kubernetes 和微服务经验。
- 已验证的工作年限、项目职责和团队管理经验。
- 是否接受远程或策略允许城市的 Onsite。
- 简单岗位信息确认。
- 是否可以发送简历。

## 9. 必须人工确认或禁止自动回答

以下内容必须进入人工确认：

- 最终薪资承诺和最低薪资底线。
- 确切到岗日期。
- 敏感离职原因。
- 电话、视频、现场面试或其他沟通的具体时间。
- 提出新的具体面试时间。
- 录用、入职或排他性承诺。
- 无法确认事实或置信度不足的回复。
- 系统主动建议发送简历，但对方没有明确索要。
- 对方要求添加微信、下载文件或跳转外部网站。
- 对方发送链接或内容存在欺诈风险。

以下内容不得自动披露，通常也不应进入可直接发送草稿：

- 身份证、银行卡、密码、验证码和账户凭证。
- 家庭隐私或法律敏感信息。
- 当前公司机密、客户名称和受保密约束的项目细节。
- 知识库中没有来源的经历、技能、学历和业绩。

## 10. 附件简历发送

系统可以管理多个网站内已上传的附件简历版本，并根据职位方向选择候选版本。

发送前必须同时满足：

1. 职位未被硬性排除且达到策略要求。
2. 对方明确要求简历，或用户确认系统主动发送建议。
3. 工作模式和地点符合策略。
4. 薪资不存在明确硬冲突。
5. 公司、行业和对话未命中黑名单或欺诈风险。
6. 选择的简历版本与职位方向匹配。
7. 网站内存在该附件，不自动上传未知文件。
8. 当前对话未发送过相同简历。
9. 用户的自动发送简历开关允许该操作。
10. 执行前再次核对附件名称和目标对话。

默认策略：

- 招聘方明确索要简历：满足全部条件时可以自动发送。
- 系统主动认为沟通已合适：必须先进入人工确认。

## 11. 人工确认队列

确认卡片至少展示：

- 平台、公司、职位和招聘人。
- 当前职位总分、等级和资格状态。
- 必要的完整对话上下文。
- 准备执行的动作和发送内容。
- 事实来源、置信度和风险提示。
- 确认、修改后发送和拒绝操作。

操作状态：

```text
PENDING
APPROVED
EXECUTING
SUCCEEDED
FAILED
CANCELLED
EXPIRED
```

状态约束：

- 只有 `APPROVED` 的确认操作可以进入 `EXECUTING`。
- 修改发送内容后必须重新执行敏感信息和权限检查。
- 执行前应再次检查任务是否过期、页面对象是否一致和开关是否仍启用。
- 失败不得自动无限重试；应记录失败原因并根据风险决定是否请求用户处理。

## 12. 对话状态

```text
NEW
ACTIVE
WAITING_RECRUITER
WAITING_USER
RESUME_REQUESTED
RESUME_SENT
SCHEDULING
SCHEDULE_CONFIRMED
ENDED
```

状态转换必须由明确事件驱动，不得仅根据大模型自由文本直接更新关键状态。

## 13. 待确认项

- B 级自动招呼开关是全局配置还是每套策略独立配置；当前建议每套策略独立配置，并受全局总开关约束。
- 招聘方明确索要简历后是否仍需默认人工确认；当前需求允许自动发送，但建议保留用户可配置开关。
- “沟通已确认岗位基本合适”的确定性条件尚未定义，系统主动发简历在条件明确前始终进入人工确认。
- 是否允许系统自动回复期望薪资区间。当前建议只允许引用用户确认过的公开期望，不允许确认最低底线或最终承诺。
