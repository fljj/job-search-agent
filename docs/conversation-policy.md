# 自动沟通与人工确认策略

## 1. 适用范围

本文定义第二阶段及后续阶段的：

- 个性化招呼语。
- 招聘方消息分析和自动回复。
- 候选人事实与敏感信息使用。
- 附件简历选择和发送。
- 人工确认队列。

电话、视频或现场面试的具体时间处理以 `scheduling-policy.md` 为唯一权威来源。

## 2. 基本原则

- 回复只能使用候选人知识库中的可信事实。
- 不存在可靠事实时不得猜测，应自动使用不承诺、不虚构的保守回复；无法安全表达时停止发送并记录原因。
- 发送前必须校验当前平台、公司、职位、招聘人和对话是否与任务一致。
- 同一招聘人、同一公司或高度相似职位应避免重复招呼和重复回复。
- 所有自动发送和人工确认操作均记录输入、决策、内容和结果。
- 用户可以全局或按平台关闭自动招呼、自动回复和自动发送简历。

所有动作统一按以下顺序决策：平台和系统状态、全局/平台/策略/动作开关、职位资格、敏感或禁止规则、动作专属条件、置信度、重复与并发检查。策略引擎最终只返回：

- `ALLOW_AUTO`：允许自动执行；
- `REQUIRE_CONFIRMATION`：仅用于电话或面试具体时间，以及独立的日历写操作；
- `DENY`：禁止执行。

任何后续条件都不能覆盖前序的 `DENY`。

### 2.1 Reply Router

普通招聘消息在进入大模型前必须经过 `conversation_agent` 的 Reply Router，固定优先级为：

1. `RULE_TEMPLATE`：到岗时间、薪资期望、地点和工作模式等确定性策略回复；
2. `KNOWLEDGE_BASE`：基于候选人资料、技能和已验证项目事实生成的结构化回复；
3. `LLM`：前两层均未命中时才调用大模型；
4. `DEFERRED`：大模型限流、超时或不可用，且前两层无法安全处理时等待 LLM 恢复，
   不生成可自动发送草稿，也不创建普通人工确认任务。

到岗、薪资、地点和工作模式规则不得为了分类而调用大模型。知识库层第一阶段直接读取
候选人资料、技能和 `knowledge_items` 中的已验证项目事实，不使用向量数据库。所有新草稿
必须记录 `reply_source`；历史草稿无法可靠反推时允许为空。

Reply Router 只负责选择草稿生成渠道，不负责授权或执行发送。草稿仍须经过现有
`PolicyDecision`、幂等检查、Action Queue 和浏览器目标复核。

### 2.2 对话记忆与重复问题防护

生成普通回复前，系统必须读取当前会话最近 200 条消息并保留消息方向，确定性构建
结构化对话记忆，包括已讨论主题、候选人已经问过的主题、招聘方已经确认的主题及最近
确认内容、尚未回答的问题和已完成的简历/联系方式动作。最近 20 条带
`INBOUND/OUTBOUND` 方向的原始消息与结构化记忆同时提供给 LLM，不能只传递没有说话人
信息的文本列表。

LLM 不得再次询问候选人已经问过或招聘方已经确认的主题。生成后程序必须再次检查问句；
发现重复问题时移除对应问句，并记录 `REPEATED_QUESTION_REMOVED`。如果移除后没有有效
内容，则使用不引入新事实的确认口径。岗位信息不足时使用的规则澄清回复也必须读取同一
份对话记忆，只询问尚未讨论的字段。

对话记忆由持久化原始消息和成功动作即时重建，不作为新的候选人事实来源，也不覆盖原始
审计数据。

## 3. 职位等级与首次沟通

评分资格状态优先于等级：任何 `FILTERED_OUT` 职位不得由 Agent 主动招呼。招聘方已经
发起的对话按 3.1 的入站规则处理。

- 80 分及以上：模型建议主动沟通且全部确定性检查通过时，自动发送首次招呼。
- 60–79 分：不主动招呼；已有入站对话继续按实际信息沟通。
- 60 分以下：不主动招呼。已有入站对话不因分数单独终止；存在明确业务冲突时才婉拒。

A/B/C 仍按 70 和 60 分划分，但等级不直接授权动作。70–79 分虽为 A 级，仍不得主动招呼。

主动招呼执行时，扫描器创建的职位详情页必须保留到动作完成后再关闭。若动作在任何页面
写入前因目标详情页不可用而失败，可以在重新读取并再次核对平台、公司、职位、招聘人和
外部职位 ID 后自动重试；已经写入、结果未知或无法证明尚未写入的动作不得自动重试。

统一权限矩阵：

| 动作 | 允许自动 | 必须确认 | 禁止 |
|---|---|---|---|
| 首次招呼 | 分数至少 80、模型建议主动沟通且全部安全条件满足 | 无 | 低于 80、硬性排除、职位非开放、平台暂停 |
| 普通回复 | 招聘方已发起对话、内容安全且未确认 `MISMATCH` | 无 | 平台暂停、禁止内容或明确不匹配后仍试图推进 |
| 不匹配婉拒 | 沟通中取得明确冲突证据 | 无 | 页面身份不匹配或已发送相同婉拒 |
| 对方明确索要简历 | 当前入站请求明确、肯定，且没有已证实硬阻断并满足发送安全条件 | 无 | 保险销售、完全无关、黑名单、欺诈、重复发送、错误目标或附件不存在 |
| 平台简历同意卡片 | 卡片提示精确匹配、尚未处理，且资格不是 `MISMATCH` | 无 | `MISMATCH`、已证实硬阻断、身份不一致或重复操作 |
| 平台联系方式同意卡片 | `ROUGH_MATCH` 或 `FULL_MATCH`，卡片提示精确匹配且尚未处理 | 无 | `UNKNOWN`、`MISMATCH`、已证实硬阻断、身份不一致或重复操作 |
| 模型识别积极反馈后发送简历 | 已有入站对话、反馈证据充分且全部发送条件满足 | 无 | 反馈不明确或其他安全条件不满足 |
| 具体时间回复 | 无 | 所有等级 | 未确认、日历结果过期或页面异常 |
| 薪资、到岗和离职原因 | 有已验证公开口径时自动；否则保守回复 | 无 | 最低底线、虚构事实或禁止披露内容 |

到岗时间的公开口径配置在求职策略 `arrival_time_reply` 中。招聘方仅询问到岗周期时，
程序可直接引用该口径自动回复，不依赖大模型；涉及具体日历日期或入职承诺时仍不得擅自
扩展该口径。

### 3.1 招聘方入站优先沟通

本规则适用于 BOSS、脉脉及未来支持的平台。招聘方先发消息时，不要求先取得 100 分
正式评分；评分只约束职位列表中的 Agent 主动招呼。

消息中取得完整职位详情后，系统仍应异步补充正式硬性过滤和评分，用于职位中心展示及
后续对话判断。每轮最多处理一个入站职位；硬性排除先于 LLM，已有会话即使达到 80 分
也不得再次创建主动招呼。评分暂不可用不影响安全的规则回复和资格成熟度判断。

对话资格成熟度按确定性证据更新：

- `UNKNOWN`：岗位信息不足。允许安全澄清；对方明确索要简历时可先发送；
- `ROUGH_MATCH`：岗位方向大致相关，且没有已知地点、模式、薪资、行业或公司硬冲突。
  允许继续沟通和推进电话沟通；
- `FULL_MATCH`：岗位方向、地点/工作模式、薪资、行业、公司及核心职责等关键信息已
  充分了解并符合策略。允许推进面试；
- `MISMATCH`：存在明确冲突。发送一次礼貌婉拒，不再发送简历或推进电话/面试。

岗位方向判断不得只比较完整职位名称。标题中明确出现策略技术词，或“系统开发、应用
开发”等相关标题的完整 JD 中存在策略技术证据时，应视为方向相关；明确无关的销售、
施工、产品等标题不得仅因 JD 中偶然出现技术词而转为匹配。

信息不足不等于不匹配，也不得为了满足旧评分接口而补全虚假 JD 或伪造分数。猎头主动
发来的消息可以回复和按明确请求发送简历，但 Agent 仍不得主动向猎头打招呼。

电话沟通的资格门槛是 `ROUGH_MATCH`；面试邀约的资格门槛是 `FULL_MATCH`。具体电话
或面试时间始终进入人工确认。

电话或面试意图必须有消息原文证据。只有明确出现“电话、通话、语音、面试、视频面”
等表达时，才能进入相应排期流程；“沟通一下、交流一下、聊聊”等泛化招聘沟通属于普通
消息，不得仅凭大模型分类升级为电话或面试确认。

`FULL_MATCH` 至少要求以下信息均已取得可靠证据，未知字段不得按默认值补全：

- 公司和招聘主体；
- 岗位名称、核心职责及主要技能方向；
- 工作地点和 Remote/Onsite/Hybrid 模式；
- 薪资范围，或招聘方明确表示该信息将在面试前可继续确认且不存在已知低于底线证据；
- 行业、正式/外包/猎头代招关系；
- 不存在公司黑名单、排除行业、保险销售、欺诈或其他明确策略冲突。

任何必需字段仍未知时最多保持 `ROUGH_MATCH`，严格禁止推进面试；可以继续文字沟通或
在具体时间经用户确认后进行电话沟通以补全信息。

### 3.2 脉脉系统推荐

脉脉平台生成的“我们正在招……人才，可以要一份你的简历吗？”推荐卡片使用独立的
`PLATFORM_RECOMMENDATION` 决策，不套用普通主动招呼和完整评分门槛。

程序只允许根据卡片当前可见信息执行受控快速判断：

- `ACCEPT_AND_SEND_PROFILE`：岗位属于技术、研发、架构、Java/后端、AI/Vibe Coding、
  直播运营或其他大致相关方向，且没有明确拒绝证据；
- `REJECT_RECOMMENDATION`：明确属于保险销售、保险代理、拉人头式销售、完全无关岗位，
  或命中公司黑名单、排除行业、欺诈及安全风险；
- `DENY`：页面身份无法唯一核对、推荐已经处理、操作控件不唯一、平台会话异常或结果
  未知且尚未完成对账。

信息缺失本身不构成拒绝理由。猎头发来的系统推荐属于对方已经发起沟通，不受“猎头
不主动打招呼”限制，但不能反向授权 Agent 对猎头主动招呼。

该流程只授权点击推荐卡片自带的“同意”或“拒绝”。后续真人消息转入 3.1 的入站流程；
普通文本回复和电话/面试推进仍按资格成熟度决策。

推荐卡片和官方通知不进入消息中心；由真实招聘人发出的普通私信必须进入消息中心。

### 3.3 Telegram 招聘频道

- 只读取 `config/telegram-policy.json` 中配置的白名单频道；
- 以频道 ID 和消息 ID 去重，只处理明确标记为招聘的帖子；
- 同一帖子包含多个编号岗位时，必须拆分为独立职位后分别评分，帖子级工作模式和联系人可
  继承，其他岗位的职责和要求不得混入当前职位 JD；
- 帖子必须提供唯一的 `@username` 或 `t.me/username` 联系方式；
- 主动私聊继续执行硬性排除、LLM 评分和 80 分门槛，不降低 BOSS 主动沟通标准；
- 只向帖子明确提供的联系人私聊，不在频道或群组中公开回复；
- 联系人缺失、格式不合法或只有邮箱时，不自动发送 Telegram 消息；
- 发送前必须使用完整用户名精确匹配联系人，不得选择模糊搜索或相似用户名结果；
- 同一帖子和同一职位只允许产生一次主动沟通动作，结果未知时不得直接重试。
- 频道帖子本身不进入消息中心；首次联系人私聊成功后建立实际会话并进入消息中心。

## 4. 个性化招呼语

招呼语至少使用：

- 职位名称和公司行业。
- JD 的核心职责和两到三个关键技能。
- 候选人与岗位最匹配的两到三个真实事实。
- 需要进一步确认的工作模式、团队或业务问题。

要求：

- 控制长度，避免堆砌全部技能。
- 不虚构项目、结果、技术或管理经验。
- 不包含身份证、家庭、银行等敏感信息。
- 不作薪资、到岗或入职承诺。
- 相似岗位的文本应有针对性差异，但不得为追求差异而改变事实。

### 4.1 BOSS 平台默认招呼

BOSS 点击“立即沟通”会直接发送平台默认招呼，不能在点击前注入单职位生成文本。
因此 BOSS 首次招呼采用 `PLATFORM_DEFAULT` 模式：

- Agent 仍使用评分、80 分门槛和模型建议决定是否发起沟通；
- 点击后必须回读平台实际发送文本并保存审计；
- 未配置固定预期文案时，观察到任意非空平台招呼即可记为成功；
- 如未来配置固定预期文案，则必须逐字一致，否则进入 `OUTCOME_UNKNOWN`；
- 不得在平台默认招呼后自动追加第二条个性化消息；
- 千问生成内容只用于匹配理由和后续对话，不冒充首次实际发送内容。

## 5. 候选人知识库

知识项至少包含：

- `fact`：可引用事实。
- `source`：简历、用户输入或经确认资料。
- `allowed_for_auto_reply`：是否允许自动使用。
- `sensitivity`：普通、敏感或禁止使用。
- `verified_at`：最近确认时间。
- `valid_until`：可选有效期。

知识库覆盖：个人介绍、工作及项目经历、技术栈、管理经验、行业经验、学历、薪资期望、地点、远程要求、到岗时间、离职原因、不可回答事项和附件简历信息。

招聘方使用“期望薪资”“薪资要求”“薪资范围”或“薪资的话，目前期望多少”等明确问法时，
系统必须优先按关联职位的工作模式读取策略薪资并使用规则回复，不调用大模型，也不得用
自我介绍、反问职级或重复询问岗位信息代替薪资答案。仅陈述岗位薪资而没有询问候选人期望
时，不应误触发该规则。

学历培养形式遵循按需披露：招聘方明确询问“是否全日制”“是否统招”“是否在职”、
“学信网是否可查”或“学历性质”时，系统应优先使用专科、本科、硕士研究生等对应层级的
已验证知识项进行确定性自动回复，不调用大模型。招聘方未询问时，招呼语和普通回复不得
主动提及候选人的非全日制或非统招学历。

候选人资料中的工作年限、管理年限、架构或核心系统经历及技能条目属于用户已确认
配置，可以作为招呼语的可信事实；生成结果必须引用对应资料或技能实体 ID。独立
知识库为空时不得忽略这些已确认资料，也不得生成占位招呼语。

JD 中的年龄限制应标记为“岗位合规提示”。在没有候选人出生信息时不得推断年龄
是否匹配，也不得把岗位合规风险表述为候选人不匹配。

缺少明确事实时，系统自动使用不承诺口径，例如：“这部分需要结合具体安排进一步沟通，目前不方便给出确定结论。”该回复不得伪装成已确认事实，也不得承诺稍后一定补充。

## 6. 消息意图

至少支持：

```text
JOB_DETAIL
TECH_STACK
WORK_EXPERIENCE
PROJECT_EXPERIENCE
MANAGEMENT_EXPERIENCE
SALARY
LOCATION
REMOTE_POLICY
ARRIVAL_DATE
RESUME_REQUEST
PHONE_CALL
INTERVIEW_INVITATION
INTERVIEW_TIME
COMPANY_INTRODUCTION
UNCLEAR
SENSITIVE
```

消息可能同时具有多个意图。时间相关意图识别后必须交给排期策略处理，不能由普通回复策略直接承诺。

普通回复应使用当前可获得的受信上下文：当前策略、已知 JD 字段、可选的最新有效评分、
匹配理由、风险、工作模式和地点。缺少正式评分不能阻止入站澄清或按明确请求发送
简历。策略偏好不能伪装成候选人经历事实；
候选人陈述仍只能引用带事实 ID 的资料或知识项。同一会话中连续到达且尚未处理的
入站消息应合并为上下文，只为最新消息生成一次回复，旧消息标记为 `SUPERSEDED`。
消息发现不得只依赖平台“未读”标记；应扫描可见会话并依据稳定的会话组合身份、最后
消息证据、消息方向和本地幂等记录判断是否需要回复。平台原生会话 ID 重复时，必须用
招聘人、职位和公司等可见字段生成稳定身份，点击后再次核对目标，无法唯一匹配则停止。
详情暂时无法打开但列表提供稳定最后消息键时，本轮仍记录该消息键，避免持续点击同一
失败项；只有最后消息发生变化后才重新读取。平台消息列表连续三轮不可用时暂停该平台，
前两次仅记录失败并继续轮询。

## 7. 回复置信度与权限

置信度只用于选择自动回复方式；除电话和面试具体时间外，普通低置信度不创建人工确认。
Rule/Knowledge 均无法处理且 LLM 限流、超时或不可用时，该消息进入等待 LLM 状态，
不得创建 `HUMAN` 草稿或普通确认任务；恢复后按原消息幂等状态继续。

- `confidence >= 0.90`：可以发送基于可信事实的自然回复。
- `0.75 <= confidence < 0.90`：发送更保守、少承诺的回复，不引用不确定细节。
- `confidence < 0.75`：仅发送澄清问题或固定安全模板；无法安全生成时暂停该条消息，不自动扩展事实。

置信度应综合：意图识别、知识命中、事实新鲜度、上下文完整性和内容风险，不能直接使用大模型自报概率作为唯一依据。

收到消息时先更新对话资格成熟度；信息足够时再创建或刷新正式评分。评分不足 60
可以作为风险证据，但不能单独阻止招聘方已发起的沟通或首次明确索要简历。职位命中
公司黑名单、排除行业、保险销售、欺诈风险，或地点、工作模式、薪资和岗位方向出现
明确冲突时，将成熟度设为 `MISMATCH` 并礼貌婉拒。

## 8. 允许自动回复的普通问题

在知识库事实明确且允许自动使用时，可以回复：

- Java、Spring Boot、Spring Cloud 等技术经验。
- 数据库、Redis、Kafka、Docker、Kubernetes 和微服务经验。
- 已验证的工作年限、项目职责和团队管理经验。
- 是否接受远程或策略允许城市的 Onsite。
- 简单岗位信息确认。
- 是否可以发送简历。

## 9. 必须人工确认或禁止自动回答

以下内容必须进入人工确认：

- 电话、视频、现场面试或其他同步沟通的具体时间。
- 提出、接受或修改具体沟通或面试时间。
- 创建、修改或删除日历事件。

以下内容不创建普通人工确认，而是自动采用安全口径：

- 最终薪资、最低薪资底线、确切到岗日期或入职承诺：仅引用用户已配置的公开口径；没有口径时明确表示暂不作承诺。
- 敏感离职原因：使用用户配置的公开离职口径，否则礼貌回避。
- 无法确认事实或置信度不足：提出澄清问题、使用固定模板或停止发送。
- 添加微信、下载文件、跳转外部网站或可疑链接：不执行外部操作，并自动回复仅在当前招聘平台继续沟通。

以下内容不得自动披露，通常也不应进入可直接发送草稿：

- 身份证、银行卡、密码、验证码和账户凭证。
- 家庭隐私或法律敏感信息。
- 当前公司机密、客户名称和受保密约束的项目细节。
- 知识库中没有来源的经历、技能、学历和业绩。

## 10. 附件简历发送

系统可以管理多个网站内已上传的附件简历版本。发送决策通过后，按稳定登记顺序选择
当前平台的第一份可用简历作为默认附件，不根据职位标题、评分或适用方向二次匹配。
适用方向仅用于资料展示。

发送前必须同时满足：

1. 招聘方已经发起对话，且当前资格成熟度不是 `MISMATCH`。
2. 对方明确要求简历，或模型从对话中识别出有消息证据的积极反馈。
3. 不存在已知的工作模式或地点硬冲突；字段未知不阻断首次明确请求。
4. 薪资不存在已知硬冲突；薪资未知不阻断首次明确请求。
5. 公司、行业和对话未命中黑名单或欺诈风险。
6. 当前平台存在已登记的默认可用简历。
7. 网站内存在该附件，不自动上传未知文件。
8. 当前对话未发送过相同简历。
9. 用户的自动发送简历开关允许该操作。
10. 执行前再次核对附件名称和目标对话。

默认策略：

- 招聘方明确索要简历：满足全部确定性安全条件时直接发送平台默认简历，不设分数门槛；
  该消息不先生成普通文字回复，也不调用回复 LLM。
- “明确索要”必须来自当前未处理的肯定请求或平台原生索要卡片，例如“请发一份简历”；
  “已查看简历”“简历不合适”“简历中没有看到某项经历”及仅提及“简历/附件”不构成
  发送授权。
- 模型识别积极反馈：必须返回引用的招聘方消息 ID、反馈类型和置信度；程序校验后，
  证据必须包含当前新消息，且当前成熟度不是 `MISMATCH` 时自动发送，不能反复使用历史
  索要简历消息创建新动作。
- 反馈不明确、模型输出无证据或置信度不足：不发送简历，继续正常沟通或等待下一条消息，不创建人工确认。
- 保险销售、完全无关、公司黑名单、欺诈、明确策略冲突或 `MISMATCH`：禁止发送。

发送任何 LLM 回复前，程序必须用已绑定职位的结构化事实复核问题。工作模式已经明确为
`ONSITE` 或 `REMOTE` 时，不得再询问是否支持远程；已知岗位事实不能被模型作为待确认
问题重复发送。

简历动作使用独立开关 `auto_resume_enabled`。`auto_resume_min_score` 只适用于 Agent
主动发现职位后产生的简历动作，不适用于招聘方入站明确索要。主动招呼门槛仍为 80。

### 10.1 BOSS 入站同意卡片

满足下述资格条件时，BOSS 对话中的平台原生卡片使用确定性规则直接点击“同意”，不生成
文字草稿，也不调用 LLM：

- “我想要一份您的附件简历，您是否同意”：`UNKNOWN`、`ROUGH_MATCH` 或 `FULL_MATCH`
  均可处理，但必须没有已证实硬阻断；
- “我想要和您交换联系方式，您是否同意”：仅 `ROUGH_MATCH` 或 `FULL_MATCH` 可处理。

BOSS 的“您是否接受此工作地点?”卡片同样使用确定性规则处理。程序必须提取卡片中的
完整地址，并与当前策略启用的 `ONSITE` 允许地点比较；地址属于济南允许范围时点击
“可以接受”（当前策略配置为济南）；不在策略允许范围或地点无法可靠识别时不点击。
该路径不调用 LLM，动作记录为
`LOCATION_CONSENT_ACCEPT`。职位信息不足本身不阻止简历卡片，但不能放宽联系方式和地点
卡片各自的确定性条件。

服务层必须把对应动作分别记录为 `RESUME_CONSENT_ACCEPT`、
`CONTACT_CONSENT_ACCEPT` 和 `LOCATION_CONSENT_ACCEPT`，保存资格快照、目标身份、
稳定指纹和审计事件。
浏览器适配器只允许执行上述精确提示，执行前重新核对唯一会话和未处理状态，执行后回读
卡片已失效或已同意的证据。点击后结果无法确认时进入 `OUTCOME_UNKNOWN`，不得直接
重复点击。`MISMATCH`、已证实硬阻断或目标身份变化时不得自动同意；`UNKNOWN` 只允许
处理符合上述条件的简历卡片。

“对方已查看了您的附件简历”等纯平台状态通知只入库为忽略事件，不进行意图分类、
回复生成或 LLM 调用。

### 10.2 脉脉推荐卡片直接投递

脉脉推荐卡片点击“同意”后，由平台直接发送候选人的平台资料和已配置附件简历。该动作
属于 `PLATFORM_RECOMMENDATION_RESUME`，与普通对话中的 `RESUME` 动作分开审计。

发送前必须同时满足：

1. 推荐卡片、招聘人和岗位在当前页面中唯一匹配；
2. 简化判断为 `ACCEPT_AND_SEND_PROFILE`；
3. 页面明确显示“同意”操作且推荐尚未处理；
4. 自动发送简历和脉脉系统推荐开关均已启用；
5. 不存在相同推荐、相同招聘人和相同岗位的成功发送记录；
6. 未命中公司黑名单、排除行业、欺诈风险或完全无关岗位；
7. 执行后能够回读“已发送简历”“你们现在可以对话了”或等价的平台成功证据。

点击“拒绝”也必须具备独立幂等键和回读证据。任何点击后的结果无法确认时进入
`OUTCOME_UNKNOWN`，在完成平台对账前不得再次处理同一推荐。

### 10.3 不匹配婉拒

入站对话取得明确不匹配证据后使用动作类型 `MISMATCH_DECLINE`。历史
`LOW_SCORE_DECLINE` 仅兼容旧记录，不再由分数单独触发。回复应简短、礼貌，不与
招聘方争论评分，也不透露内部黑名单或完整求职策略。

我方成功发送明确婉拒后，会话状态设为 `DECLINED`；招聘方明确表示候选人不合适、
不匹配、不再推进或岗位已关闭后，会话状态设为 `ENDED`。浏览器读取到用户在平台上
手动发送的明确婉拒时，同样设为 `DECLINED`。这些状态均表示不再进一步沟通，消息
发现阶段直接排除，不再打开会话、生成回复或发送简历。疑问句或仅讨论某项条件是否
合适，不得据此终止会话。

用户明确撤销先前婉拒并要求继续沟通时，可以通过受审计的重新开启操作恢复为
`ACTIVE`。平台上较新的我方消息明确表达“岗位符合我的方向”或“可以继续沟通”时，
该纠正信息优先于更早的婉拒；重新开启本身不得自动发送消息，必须等待招聘方新回复。

允许公开的原因：

- 工作地点或工作模式与当前计划不一致；
- 薪资区间与当前考虑范围存在明显差异；
- 岗位方向、技术重点或职责与当前求职方向不完全匹配；
- 当前阶段暂不考虑该类岗位。

公司黑名单、内部风险标签、模型置信度、具体分数和候选人隐私不得作为对外原因。多项
原因同时存在时最多选择两个最中性、证据最明确的原因。相同对话只发送一次不匹配
婉拒；后续消息默认不再自动回复，除非招聘方提供的新岗位信息消除原冲突并使资格成熟度
重新达到 `ROUGH_MATCH` 或 `FULL_MATCH`。

## 11. 人工确认队列

人工确认队列只承载电话、面试具体时间和日历写操作。普通消息、招呼、不匹配婉拒和
简历发送不得因模型不可用创建确认卡片；无法安全降级的普通消息等待 LLM 恢复。

确认卡片至少展示：

- 平台、公司、职位和招聘人。
- 当前职位总分、等级和资格状态。
- 必要的完整对话上下文。
- 准备执行的动作和发送内容。
- 事实来源、置信度和风险提示。
- 确认、修改后发送和拒绝操作。

操作状态：

```text
DRAFT
PENDING_APPROVAL
APPROVED
EXECUTING
SUCCEEDED
FAILED_RETRYABLE
FAILED_FINAL
CANCELLED
EXPIRED
SUPERSEDED
OUTCOME_UNKNOWN
```

状态约束：

- 只有 `APPROVED` 的确认操作可以进入 `EXECUTING`；自动允许的动作必须保存对应的 `ALLOW_AUTO` 策略决策后才能进入 `EXECUTING`。
- 修改发送内容后必须重新执行敏感信息和权限检查。
- 执行前应再次检查任务是否过期、页面对象是否一致和开关是否仍启用。
- 失败不得自动无限重试；应记录失败原因并根据风险决定是否请求用户处理。
- 明确发生在任何点击之前的目标标签页不存在或不唯一，应进入
  `FAILED_RETRYABLE`。历史上误记为 `FAILED_FINAL` 的同类失败，仅在失败码属于
  服务端白名单、用户再次确认且页面重新核验通过时允许重新批准。
- 外部结果无法确认时进入 `OUTCOME_UNKNOWN`，先回读平台对账，不得直接重试。
- 修改内容后原动作进入 `SUPERSEDED`，新版本重新决策或审批。
- 重复请求使用相同幂等键并返回原动作，不创建第二个可执行动作。

## 12. 对话状态

```text
NEW
ACTIVE
WAITING_RECRUITER
WAITING_USER
RESUME_REQUESTED
RESUME_SENT
SCHEDULING
SCHEDULE_CONFIRMED
ENDED
```

状态转换必须由明确事件驱动，不得仅根据大模型自由文本直接更新关键状态。

## 13. 自动化配置与不变量

独立配置项至少包括：

- `auto_greet_enabled`；`auto_greet_min_score` 首版固定为 80，只允许未来提高，不允许降低；
- `auto_reply_enabled`、`auto_reply_min_confidence`；
- `auto_resume_enabled`；`auto_resume_min_score` 只约束非入站简历动作；
- `maimai_recommendation_enabled`：是否自动处理脉脉系统推荐，默认关闭；
- `maimai_recommendation_resume_enabled`：是否允许推荐判断通过后点击“同意”并使用平台
  能力发送资料和简历，默认关闭且只能在前一开关启用时生效；
- `mismatch_decline_enabled`、不匹配婉拒模板；旧 `low_score_decline_enabled` 仅用于
  数据迁移兼容；
- 全局、平台和策略级暂停开关；
- 频率限制和每日动作上限。

以下规则不可配置绕过：低于 80 分不能主动招呼；`MISMATCH` 对话不能继续发送简历或
推进电话/面试；电话具体时间必须确认；未达到 `FULL_MATCH` 不能推进面试；面试具体
时间必须确认；无事实支持不得作肯定陈述；禁止披露敏感信息；页面身份不匹配必须
停止；`OUTCOME_UNKNOWN` 不得盲目重试。

“积极反馈”必须由模型返回可追溯的招聘方消息证据，程序校验消息属于当前对话且未被撤回。系统只可自动引用用户确认过的公开薪资、到岗和离职口径，不得虚构最低底线或最终承诺。

## 14. LLM 能力分区熔断

认证或余额异常、限流、超时、网络及模型服务故障会打开用户级 LLM 熔断器。熔断期间
停止新 LLM 解析、评分、主动招呼和开放式 LLM 回复，不再逐职位或逐消息调用模型；
确定性硬过滤、Rule/Knowledge 回复、满足第 10 节条件的明确简历请求和平台原生卡片、
只读对账、租约回收及维护任务继续运行。

Rule/Knowledge 均无法安全处理的普通消息进入等待 LLM 状态，不发送占位回复，不创建
普通人工确认，也不反复生成草稿。系统只允许一个最小健康探测请求；自动或用户手动
探测成功后恢复 LLM 相关队列，并沿用原幂等状态继续处理。

电话和面试具体时间及日历写入仍按排期策略进入人工确认，与 LLM 是否可用无关。

## 15. 身份、简历请求与终态会话

- “猎头”是招聘方角色，不是岗位方向；缺少 JD 时资格保持未知，不得仅因猎头身份判定岗位
  不匹配。主动职位发现是否向猎头招呼仍服从策略。
- 只有包含明确索要动作的正文或平台原生简历卡片才属于简历请求；正文仅出现“简历”“附件”
  等名词不自动发送。
- 明确结束沟通必须保存终态消息证据。列表末条未变化时不再进入详情；出现普通新消息也不
  自动复活，只有新岗位或明确纠正、重新沟通表达才建立新 episode。
- 派生且不可靠的会话或消息身份只能进入人工核验，不能自动回复或发送简历。

## 16. R3 能力队列与记忆版本

- 规则、知识库、明确简历请求和平台原生卡片属于无 LLM 队列；开放式生成、职位语义解析
  和评分属于 LLM 队列。模型熔断只暂停后一类能力。
- 开放式消息保存为 `WAITING_FOR_LLM`，不生成 `HUMAN/REQUIRE_CONFIRMATION` 草稿；
  模型恢复后按原消息 ID 继续，唯一草稿指纹防止重复生成。
- 对话记忆只读取当前 conversation episode。旧 episode 作为审计历史保留，但不能永久压制
  新一轮合理追问；草稿指纹同时绑定资格版本和知识库事实版本。
